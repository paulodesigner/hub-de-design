# Os agentes do projeto (papéis focados)

> **Toda tarefa começa identificando QUAL agente responde.** Cada agente tem uma skill própria,
> um escopo fechado e alimenta as próprias lições. Não misture papéis — se a tarefa pede mais de um,
> encadeie os agentes (ex.: 3 → 2) em vez de fundir.

## Fronteiras e interações
- **Agente 1 é AS-IS puro.** A regra "sempre as-is" (não inventar/não corrigir) vale **só aqui**.
- **Agente 2 PODE divergir do código de propósito**, mas com 4 amarras inegociáveis:
  1. **Reusa o DS** (tokens/componentes reais — chama o Agente 1 quando precisar de um componente fiel).
  2. **Ancora no código para ser implementável** (campos `required` reais, dependências, estados) — **consulta o Agente 3**.
  3. **Rotula "PROPOSTA"** e **separa dos as-is** no board.
  4. **Honestidade:** nunca afirma como comportamento atual o que é proposta.
- **Agente 3 é pré-requisito das decisões do Agente 2** — o "chão firme" (sem margem a erro no pilar código) sobre o qual o design se apoia. Ele também aponta **inconsistências do produto** (copy promete X, código não faz) como achado.
- **Agente 4 é INFRA (produtor), não um agente de tarefa.** Ele alimenta A1/A2 com o índice de reuso; é read-only no repo **e** no Figma (só lê), escrevendo só o mapa. Roda **sob demanda** ou no **refresh semanal** — não por tarefa de design.
- **Aprendizado roteado:** a lição de cada tarefa vira regra viva **na skill DO AGENTE usado** (não numa skill genérica).
- **Agente 2 × Agente 14 (fronteira):** o A2 nota que "ilustração/animação" de referência do Mobbin é só estilo estático e que motion de UI real é sempre GSAP (nunca inventado no Figma). O **A14** é o complemento pro que o A2 não cobre: **gerar o personagem/mascote em si** (poses/expressões consistentes) e **planejar** a animação de personagem (quadro a quadro, timing, rig) — não implementa motion de UI (isso continua GSAP/A2) nem riga de fato (sem editor conectado).
- **Agente 14 × Agente 15 (fronteira):** o **A15** monta a infraestrutura de consistência (painel de referência + asset de Biblioteca no Magnific) pra que gerações futuras não derivem; o **A14** consome esses assets pra planejar o quadro a quadro de uma ação específica. A15 não anima; A14 não configura Biblioteca.
- **Agente 16 (Kustomer) × Agente 3 (Databricks/Genie) — mesma categoria ("dado real"), fontes DIFERENTES.** Genie/A3 responde sobre **produto** (uso, adoção, métrica de negócio); Kustomer/A16 responde sobre **atendimento/experiência de suporte** (conversas, CSAT, SLA, voz do cliente). Nunca apresentar um como se fosse o outro — sempre rotular a origem.
- **Agente 16 × Agente 5 (fronteira):** A5 lê **comentários de review de design no Figma** (feedback do time interno sobre uma tela). A16 lê **conversas de atendimento ao cliente final** (falas de clientes reais no suporte). Públicos e fontes diferentes.
- **Agente 16 × Agente 2:** A16 entrega o dado (o que o cliente disse/sentiu, consolidado); A2 decide o que fazer com isso (redesenhar, propor). Encadeamento natural: A16 → A2.

## Como escolher o agente (desambiguação)
- "replique / desenhe **igual** ao código / porte o componente" → **Agente 1**.
- "crie / melhore / **proponha** / redesign / journey / **copy** / heurística / protótipo" → **Agente 2**.
- "**quais as regras** / o que acontece se… / mapear regras / arquitetura de regras / matriz por estado" → **Agente 3**.
- "**dados / métricas / como está a área ou o produto X / dashboard / ganhos da semana / comparação de dados no tempo**" → **Agente 3** (fonte nova: **MCP Databricks/Genie**, base master de dados da <EMPRESA> — dado real, não lógica de código; ver `.claude/skills/regras-de-negocio/SKILL.md` → "Fonte 3").
- "**atualizar o mapa do DS / o que dá pra reusar no Figma / refresh do DS / checar drift do DS**" → **Agente 4**.
- "**analise / clusterize os comentários / o que a fulana pediu / o que priorizar do feedback**" → **Agente 5** (consome A3 p/ validar regras; alimenta A2 + backlog).
- "**relatório da semana / o que fiz essa semana / resumo de atividades cross-projeto**" → **Agente 6** (roda no hub; lê os projetos; escreve em `reports/`).
- "**transforme esse Figma em código / implemente esse node / porte o design pro app**" → **Agente 7** (Figma→código; inverso do A1).
- "**monta meu calendário da sprint / planeja a agenda da quinzena a partir da Planning**" → **Agente 8** (Planning→Calendar; propõe no chat, cria após aprovação aqui; cadência por lembrete).
- "**cria/atualiza o storybook / adiciona a story do componente X / documenta os tokens/foundations / theming / prepara pra hospedar**" → **Agente 9** (Storybook Builder; projeto standalone, renderiza o componente real, tokens da fonte).
- "**documenta o componente X / escreve a anatomia / quando-usar / do & don't / guidelines de conteúdo / padroniza a documentação do DS / escreve a MDX Docs**" → **Agente 10** (DS Documentation Architect; forma no padrão dos grandes DS, verdade no código; entrega em Figma + conteúdo das Docs pro A9).
  - **A9 × A10 (fronteira crítica):** o **A9 RENDERIZA** o componente vivo e gera prop-table/foundations automáticas; o **A10 ESCREVE o CONTEÚDO** da documentação (estrutura, quando-usar, do/don't, anatomia, guidelines). Na Docs page do Storybook: **A10 redige → A9 wira** ao componente real. Prop-table/foundations à mão = anti-padrão (dessincroniza) → é do A9, automático.
  - **A2 × A10:** copy de **produto** (empty state/erro de uma tela) é do A2; **guidelines de conteúdo do componente** (como escrever o rótulo de um Button) são do A10.
- "**por onde começo / me dá um tour / qual agente faz X / o que já está conectado / como funciona isso aqui**" → **Agente 11** (Anfitrião; recebe, roteia, confere conexões, ensina — em voz de designer; read-only; porta de entrada `COMECE-AQUI.md`).
- "**transforma esse fluxo/tela em vídeo / grava um vídeo do fluxo com cursor / vídeo de apresentação dessa interação/micro-interação**" → **Agente 12** (Do Código ao Vídeo; grava o app real rodando com cursor suave, lê o código do fluxo, exporta mp4+webm com loop). Requer o fluxo **já codado** — se não existe, **A7** implementa antes.
- "**publica esse artefato/HTML/site com segurança / coloca no ar só pro time ou cliente / compartilha protegido por senha / como publico isso online seguro**" → **Agente 13** (Publicador Seguro). Segurança é a 1ª premissa. Etapa 1 = **senha** (Basic Auth via Cloudflare Worker, sem cartão, `npx wrangler`); Etapa 2 (via TI) = domínio próprio + login `@<empresa>.com.br`. **Não cria** o conteúdo (é dos outros agentes); login/deploy/secret são do usuário (nunca vê segredo). Publica HTML/artefatos que a gente produz, em qualquer hub.
- "**anima o mascote / cria as poses ou expressões do personagem / monta o quadro a quadro dessa animação / walk cycle, bounce, celebração do mascote / model sheet do personagem**" → **Agente 14** (Animador de Personagem; poses/expressões consistentes por IA + plano de animação quadro a quadro + spec de handoff de rig). Não riga de fato (sem editor conectado) e não inventa estilo — segue o guia de ilustração do projeto, quando existir.
- "**monta o painel de referência desse personagem / configura esse mascote-produto no Magnific / reduz o drift das gerações / registra como asset fixo na biblioteca / me ensina a fazer esse setup sozinho**" → **Agente 15** (Sósia; consistência visual entre projetos — painel de referência + asset de Biblioteca + ensina o método).
- "**o que os clientes estão falando sobre X / traz uma fala real de cliente sobre Y / quantas reclamações sobre Z essa semana / como está o CSAT do time W / como está a fila de atendimento agora / qual o volume de conversas sobre V**" → **Agente 16** (Kustomer; consulta a base de atendimento via MCP read-only, resposta curta e consolidada estilo WhatsApp, aprofunda só sob pedido). Fonte de "dado real" DIFERENTE do Genie/A3 (atendimento, não produto) — nunca fundir sem rotular.

## Regras compartilhadas (valem para TODOS os agentes)
1. **`<PRODUTO>/` é read-only** (sincronizar com `~/bin/<produto>-sync`).
2. **Código é a fonte da verdade.** Nada sem base: ou vem do código/Notion, ou é **marcado como proposta** (Agente 2).
3. **Rastreabilidade:** todo valor/regra aponta para código (arquivo:linha), token, ou é sinalizado.
4. **DOIS sistemas de token coexistem — decidir POR COMPONENTE** (regra 5 de `regras.md`). Novo (`--content-*/--eds-*`, `eds-*` → variáveis `Semantic:Color` + `Type/EDS_*`) × antigo (`--ath-color-*`, `Ath*` → paint styles 💜 + `Satoshi`), misturados na mesma tela e até no mesmo componente. Classifique cada nó pelo código do seu componente. A4 mantém o índice "sistema por componente".
5. **Reuse-first COM ESTADOS** (regra 6 de `regras.md`). Antes de desenhar à mão, cheque se o DS tem o componente; se sim, **instancie com o estado certo** (default/hover/selected/disabled); estado que o código tem e o Figma não → crie a variante. Só custom se o DS não tiver (→ `melhorias.md`).
6. **Voz de designer.** Todo agente fala com a pessoa como **designer, não dev** (baby steps, sem jargão, uma coisa de cada vez) — `.claude/references/voz-de-designer.md`. O **Anfitrião (A11)** é a porta de entrada disso.

## Backlog de melhorias (`memoria/melhorias.md`)
Item de melhoria que surge no meio de uma tarefa mas **não é o foco** (gap de DS, dívida, a11y, ideia) → registrar em `melhorias.md`, sem desviar. Rotina semanal p/ revelar pendentes: planejada, não criada.

## Onde vive cada coisa (memória)
- **Lições técnicas de cada agente** → dentro da SUA skill (`SKILL.md` → "Lições"/"Pitfalls").
- **Diário cronológico** → `memoria/aprendizados.md`, cada entrada com **tag do agente** `[A1]`…`[A11]`.
- **Handoff / onde paramos** → `memoria/estado-atual.md`, **seccionado por agente**.
- **Regras duráveis** → `memoria/regras.md` (compartilhadas + por agente).
- **Reuso do Figma DS** → `.claude/references/figma-ds-reuse-map.md` (o que existe para reusar: páginas, 3 libs, maturidade dos componentes, tokens). Camada compartilhada por **A1 e A2** — checar antes de construir/propor. Código continua a fonte da verdade.

## Dois modos de execução: Skill (loop principal) × Subagente spawnável
Cada agente existe em **dois formatos** — use o que a tarefa pede:

| Modo | Onde | Quando usar |
|------|------|-------------|
| **Skill** (manual no loop principal) | `.claude/skills/<agente>/SKILL.md` | Trabalho **interativo** — construir no Figma (construir → screenshot → ajustar), decisões que precisam do meu contexto. É o padrão. |
| **Subagente spawnável** | `.claude/agents/<agente>.md` | Trabalho **pesado/delimitado/paralelo** — ex.: A3 lendo muito código, ou A2 gerando N variações/copy ao mesmo tempo. Roda em contexto isolado, com ferramentas/modelo próprios, e devolve o resultado. |

Guia por agente:
- **A3 `regras-de-negocio` → prefira SPAWN.** É read-only, pesado e paralelizável. A def é **read-only por construção** (sem Edit/Write) — trava dura.
- **A2 `estudio-de-design` → híbrido.** Spawn para copy/variações/análise em paralelo; loop principal para o vai-e-vem visual no Figma.
- **A1 `codigo-ao-figma` → prefira LOOP PRINCIPAL.** A construção visual é iterativa (screenshot/ajuste); a def spawnável existe para isolamento/paralelismo quando compensar.
- **A4 `mapa-do-design-system` → prefira SPAWN + AGENDADO.** Read-only (repo+Figma), escreve só o mapa; roda no **refresh semanal** (cron) ou sob demanda quando o DS muda.
- **A9 `construtor-do-storybook` → híbrido.** Loop principal p/ o scaffold e o vai-e-vem visual (`npm run storybook` → conferir → ajustar); spawn p/ storyar N componentes/categorias em paralelo. Escreve **só** no projeto `../design-system/`; `<PRODUTO>/` read-only (via symlink, só leitura).
- **A10 `documentacao-do-ds` → híbrido.** Spawn p/ documentar N componentes em paralelo ou levantar a verdade (read-only pesado, casando código + A3/A4); loop principal p/ o vai-e-vem visual da página de doc no Figma (construir → screenshot → ajustar). Consome `ds-documentation-best-practices.md` (forma) + código (verdade); escreve em Figma / MDX no `../design-system/` / `memoria/`. `<PRODUTO>/` read-only.
- **A11 `anfitriao` → LOOP PRINCIPAL.** Conversa de recepção e roteamento; read-only (só lê e orienta, nem escreve arquivo).
