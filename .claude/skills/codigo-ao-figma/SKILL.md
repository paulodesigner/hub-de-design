# Code → Figma (réplica fiel, sem adivinhação)

> **Agente 1 de 3** (ver [`memoria/agentes.md`](../../../memoria/agentes.md)): **réplica fiel as-is**. Design novo/melhorias → agente `estudio-de-design` (A2); regras de negócio → agente `regras-de-negocio` (A3).

Replicar no Figma **exatamente** o que um componente faz no código do <PRODUTO>. O **código é a fonte da verdade** — não desenhe a partir de screenshot sozinho, e **não** importe o modelo de outro componente do DS (ex.: o `Card - Button`) quando ele divergir do componente real. Veja a memória `code-is-source-of-truth`.

> **Filosofia: copy-paste do código para o Figma, SEMPRE AS-IS.** O objetivo é uma **réplica exata do componente como ele é** — então **NÃO corrija nem "melhore"** o que o código faz (contraste, espaçamento, cor estranha, ícone faltando, etc.). Replique inclusive as falhas e apenas **reporte-as**. "Corrigir" aqui significa apenas alinhar o Figma ao código quando o desenho divergiu dele — nunca alterar o comportamento/aparência que o código produz.
>
> **ESCOPO (inegociável): esta skill é SÓ réplica fiel — copy-paste do código.** Melhorias/design novo = agente **`estudio-de-design` (A2)**; regras de negócio = agente **`regras-de-negocio` (A3)**. Aqui você **não sugere, não oferece e não aplica** nenhuma melhoria (contraste, acessibilidade, ajuste de cor/spacing, ícone "que deveria ter", etc.). Você só **replica fielmente** e **lista os achados** (divergências/falhas) como observação — sem propor conserto. Quem audita/melhora é o `estudio-de-design`; quem mapeia regra é o `regras-de-negocio`. Se algo no código parece errado, **mantenha fiel e reporte**; não decida por estética.
>
> **100% = aparência + COMPORTAMENTO.** Réplica fiel não é só "parecer igual" parado — é **funcionar e se comportar** como em produção. Se o componente faz algo interativo (expandir/recolher um submenu, abrir/fechar, alternar, selecionar), isso tem de acontecer **dentro do próprio componente** no Figma, via **componente interativo** (eixo de variante por estado interativo + reação de protótipo `ON_CLICK → CHANGE_TO` com smart-animate) — sem depender de montagem externa nem de trocar o container inteiro. Ex. real: clicar em "Integração" expande/recolhe Remessa/Retorno na própria instância (variante `Submenu=Collapsed/Expanded`, caret-right↔caret-down), espelhando o `subMenuOpened` do SFC. Ver Lição 9.
>
> **Nunca invente estados/variantes que o código não tem.** Se um estado (focus/pressed/disabled/loading…) não está no CSS daquele componente, ele **não existe** no Figma — mesmo que pareça que "deveria ter". O DEFAULT é não criar. Só crie um estado fora-do-código se o usuário **insistir explicitamente** que quer um deliberado; nesse caso marque-o como "não-código". Ex. real: o `MenuItem` do sidebar tem SÓ Default/Hover/Active no SCSS — não tem focus/pressed/disabled, então não foram criados.

## Regras de ouro (inegociáveis)

1. **Sem adivinhação.** Todo valor (cor, spacing, radius, fonte, estado) vem do código ou de um token resolvido. Se algo não estiver no código, **pergunte** — não invente.
2. **Repo é read-only.** Nunca edite o repositório `<PRODUTO>/`. Só leitura. Rode `~/bin/<produto>-sync` antes de começar (ver memória `repo-read-only-policy`).
3. **Tokens vinculados, não hardcoded — e no SISTEMA certo, por componente.** Resolva os CSS vars/SCSS do código → estilo/variável correspondente do Figma e vincule (`setFillStyleIdAsync`/`setBoundVariable`). **O <PRODUTO> tem DOIS sistemas de token coexistindo (novo `--content-*/--eds-*`/`eds-*` × antigo `--ath-color-*`/`Ath*`), inclusive misturados numa mesma tela e num mesmo componente** — classifique **cada nó** pelo código do seu componente e vincule ao sistema DELE (ver Lição 13). Hardcode nunca: se nenhum token do DS bate o valor exato, crie **estilo/variável LOCAL `<PRODUTO>/código/*`**.
4. **Fonte real.** Use a família/peso reais (ex.: Satoshi Bold/Medium). **Verifique** o nome do estilo via `listAvailableFontsAsync()` antes de aplicar (`"Bold"` ≠ `"SemiBold"` vs `"Semi Bold"`).
4a. **Se no código é um COMPONENTE, no Figma é COMPONENTE + INSTÂNCIA — NUNCA desenhe o elemento cru/hardcoded.** Antes de "desenhar" qualquer coisa, veja se o template usa um componente (`eds-button`, **`eds-button-icon`**, `nav-search`, `ath-input-*`, `ath-badge`, `ath-tag`, etc.). Se usa → crie/reuse ESSE componente no Figma e **instancie**. Erro real recorrente: desenhei os ícones do topo (eye/bell) como `<ath-icon>` soltos — mas no código são **`eds-button-icon` (Icon Button, tertiary)**; o certo é um componente Icon Button instanciado (com swap de ícone + estados), não um ícone hardcoded. Pergunta de verificação por elemento: "isso é uma tag de componente no `.vue`? então tem que ser instância de componente no Figma."
5. **O ENTREGÁVEL é sempre COMPONENTE(S) — NUNCA um mock/default estático.** Não basta "desenhar igual": o resultado tem de ser **componente Figma** (component/-set) com **todos os estados do código** alcançáveis na instância. O elemento **repetível** (linha de tabela, item de lista, card) vira um **COMPONENTE** próprio; a montagem (tabela/lista) usa **instâncias** dele (header + N instâncias de `Row`), não 5 frames desenhados à mão. Cada estado/variação do código → variante (ou instância de um sub-componente-set: status, badge, botão). Antes de fechar, valide que dá para chegar em **cada estado** trocando variante/instância — se algo só existe "pintado" numa linha fixa, não está pronto.
6. **SEMPRE 100% — todas as variantes E status, nunca só o estado do print.** O screenshot mostra UM estado; o componente tem todos. Antes de fechar, **enumere os eixos de variação a partir do código** — props enum/boolean, `computed` de estilo, mapas (ex.: `iconsEnrollmentStatus`/`styleEnrollmentStatus`), `v-if`/`v-else-if` encadeados, estados CSS (`:hover`/`:focus-visible`/`:active`/`:disabled`) — e **construa o conjunto inteiro** como component set. Cada valor de enum = uma variante (ícone+cor+label próprios); cada flag independente = um eixo/propriedade adicional. Para não explodir a matriz (N×M×K), **modele eixos independentes como propriedades separadas** (variant axis para o principal; boolean/INSTANCE_SWAP/variante de sub-componente para os ortogonais) e **reuse sub-componentes como instâncias** (badge/tag = sets próprios instanciados). Replique exatamente como o CSS define; não invente estados ausentes nem pule os existentes.
7. **Reuse o oficial — COM ESTADOS.** Ícones e subcomponentes → **instancie** os componentes oficiais do Figma (`search_design_system` → `importComponentByKeyAsync`), **nunca desenhe uma cópia flat** do que o DS já tem como componente. Se o DS tem o componente com estados (Default/Hover/Selected/Disabled…), use a instância e o estado certo; se falta um estado que o código tem, crie a variante. Só desenhe custom quando o DS **não** tiver o componente (e registre em `melhorias.md`). Ver Lição 14.
7a. **Comportamento interativo também é fidelidade.** Toda interação que o código executa (toggle, expand/collapse, open/close, seleção) deve ser **reproduzível na instância** como componente interativo (variante por estado + reação `ON_CLICK → CHANGE_TO`, smart-animate). Não basta as variantes existirem soltas — a instância tem de **alternar sozinha** no modo apresentação, igual produção.
8. **Valide sempre.** Após construir: `get_screenshot` + checagem de **contraste WCAG AA** (ver `references/wcag-contrast.py`). Reporte pass/fail por par. **Se o projeto for buildável/servível localmente, valide contra o APP RODANDO DE VERDADE, não só contra a leitura do CSS** — suba um servidor local (`python3 -m http.server` pra estático, `npm run dev` etc.) e compare screenshot a screenshot (Playwright) com o que foi construído no Figma. Um valor de espaçamento pode bater 100% com o CSS e o layout ainda sair "errado" se o ELEMENTO que carrega esse espaçamento foi simplificado (ex.: uma label de grupo no código é uma linha de altura fixa com `display:flex;align-items:center`, não o texto cru — a diferença de altura em si já é espaçamento "invisível" que some se você só copiar o texto). Achado real: `right:2px` do CSS vira `x = containerWidth - 2 - elementWidth` no Figma, não o valor absoluto "que parecia certo" — copiar o pixel visual sem fazer essa conta estourou um badge 2px pra fora do `clipsContent`.

## Workflow (fim-a-fim)

### 1. Sincronizar (read-only)
`~/bin/<produto>-sync` → garante a última versão do repo.

### 2. Localizar o componente no código
- Ache o `.vue` (SFC), seu `<style>`/SCSS, e subcomponentes/ícones que ele usa (grep por nome, import, classe).
- Identifique a fonte dos tokens: `webclient/.claude/references/design-tokens.md`, `webclient/src/assets/scss/themes/` (`_educ_colors.scss`, `_educ_typography.scss`, `root.scss`). Ver memória `<produto>-design-tokens`.

### 3. Spec profunda (a partir do código)
Extraia e anote, **com valores concretos**:
- **Layout**: direção (flex/grid → auto-layout), `gap`, `padding`, `align/justify`, `width/height`, `min/max`.
- **ESPAÇAMENTO vem do código — meça, NÃO chute (`gap`/`padding`/`margin`/posição).** As classes utilitárias do <PRODUTO> **codificam o px no nome**: `ath-ml-8` = margin-left **8px**, `ath-mr-16` = **16px**, `ath-pt-4`/`ath-pb-4` = **4px**, `ath-p-16` = **16px** (base rem 10px → o número É o px). Também leia `margin`/`padding`/`gap`/`item-spacing` no SCSS e regras como `.section-header { margin-bottom: 1.6rem }` (16px entre filtro e tabela) ou `.section-header-filter > div { margin: 0 5px }` (~10px entre itens). Erros reais por chutar: título a 16px do hambúrguer (era `ath-ml-8` = 8px), gaps de filtro a 12px (era ~10px), gap filtro→tabela a 24px (era 16px). **Para cada gap/padding/margem, aponte a classe/regra de origem** — se não achou, `getComputedStyle` do app; nunca "ficou bom no olho".
- **Radius / borda**: `border-radius`, `border-width`, `stroke-align` (inset → INSIDE; outline → OUTSIDE).
- **Tipografia**: família, `font-size`, `font-weight`, `line-height`, `letter-spacing` por elemento.
- **Cores**: cada CSS var (`--ath-...`, `--eds-...`) usada por propriedade (bg, text, border, icon) e por estado.
- **Estados**: o que muda em `:hover`/`:focus-visible`/`:active`/`:disabled` (bg, border, shadow, text, outline/ring, offset).
- **Efeitos**: `box-shadow` (→ DROP_SHADOW: offset/radius/spread/cor+alpha), transições.
- **Conteúdo/props**: textos, ícone (nome Phosphor etc.), variantes/props booleanas.
- **Estados compostos = tabela por sub-elemento.** Um seletor como `.active` costuma colorir partes DIFERENTES com vars DIFERENTES. Ex. real do sidebar: `.active > a` usa `$color-active` (#96B4C6, cor do link/borda-esquerda), mas `.active span template` (a LABEL) usa `$color-text-active` (#F8F8F8, branco) e `.active .icon-menu` usa `bg:$color-active; color:$color-icon-active`. **Nunca reaproveite a cor de um sub-elemento para outro** — monte uma tabela `{sub-elemento → propriedade → var}` antes de pintar. (Erro cometido: usei a cor do `a` para a label.)
- **Assets (logo/imagem) têm cor própria — não invente.** Extraia a cor/estilo real do asset ou do código; nunca aplique uma cor "provável". Ex.: o logo do app é o wordmark **roxo (brand)**, não branco.
- **Traduza os construtos do `.vue` → Figma** com `references/vue-to-figma-map.md` (cheat-sheet: `v-if` vs `v-show`, `v-for`→instâncias, props→propriedades, slots→INSTANCE_SWAP, `@click` toggle→componente interativo, etc.). Evita interpretar errado o que vira variante, visibilidade ou instância.
Opcional: gere a spec com a skill `/component-spec`.

### 4. Mapear tokens código → variável Figma (POR COMPONENTE — os dois sistemas coexistem)
- **Primeiro classifique o sistema de cada CSS var** (novo `--content-*/--background-<role>/--eds-*` → **`Semantic: Color`** + `Type/EDS_*`; antigo `--ath-color-*/ath-text-*` → **paint styles 💜** + `Satoshi/*`). Um mesmo componente pode ter propriedades nos dois — mapeie cada uma para o sistema dela. Ver Lição 13 + `figma-ds-reuse-map.md` → "DECISÃO CRÍTICA". Ignore CSS var **local** (`--border-color` no próprio `<style>`) — resolva à origem.
- Para cada CSS var, ache a variável/estilo equivalente no Figma (`get_variable_defs` no node, ou listar coleções `Semantic: Color`, `Semantic: Type`, `Global tokens`, `Unit` + paint/text styles do 💜).
- **Resolva a cadeia de alias** até o valor concreto (modo Light) para conferir o valor real — ver `references/figma-snippets.md` (`resolve()`).
- Se um token do Figma divergir do código (ex.: `Border/Border Primary` = #737373 vs borda clara do app), **sinalize ao usuário** e pergunte qual seguir (regra 1).

### 5. Construir no Figma (incremental)
- Carregue `figma-use` (+ `figma-generate-library`). Trabalhe em passos ≤10 operações; valide a cada passo; **retorne os IDs** de tudo criado/alterado.
- Use `figma.createAutoLayout(...)` para containers com filhos relacionados. Vincule variáveis com `setBoundVariableForPaint`.
- **Mapeie a árvore de componentes do código → sub-componentes no Figma.** Se o `.vue` importa outro SFC (ex.: `SideBar.vue` → `MenuItem.vue`), crie **cada sub-componente como seu próprio component set** (ex.: `MenuItem` com `State=...`) e instancie no container — não desenhe só o container com os filhos achatados. O container vira instâncias do sub-componente.
- **Estados de CADA componente vêm do SEU CSS — só os que existem.** Crie o default como COMPONENT, clone+reestilize por estado, `combineAsVariants`, nomeie no padrão do arquivo (`State=…`/`Propriedades=…`). Cuidado para não criar estados que o código NÃO tem (ver Lição 4); e não esquecer os que ele TEM (hover/active/selected/disabled/loading conforme o SCSS).
- Reuse ícones oficiais via `importComponentByKeyAsync(...).createInstance()`.

### 6. Validar
- `get_screenshot` do componente e do set; compare visualmente com o código/app.
- **Ground-truth quando o valor for ambíguo/crítico: leia o ESTILO COMPUTADO do app rodando** (`localhost:8080`, `getComputedStyle(el)`), não a cascata do SCSS. O DOM renderizado é a saída real do código e resolve `var()`/herança/override/`currentColor`. Ordem: **render computado > leitura de SCSS > suposição (nunca)**. Ver `references/fidelity-and-verification.md`.
- **Cross-check contra PRODUÇÃO (obrigatório quando houver print/app real).** Antes de declarar pronto, peça/use um screenshot do componente rodando em produção e compare lado a lado: logo (cor/forma), cor de cada estado (em especial o **ativo**: label vs ícone vs fundo), tamanhos, ordem dos itens. O CSS pode ter overrides/heranças que só aparecem renderizados. Se não houver print, **pergunte** se existe um antes de finalizar.
- **Passe de dúvida (rápido):** para cada valor não óbvio, tente refutá-lo ("que evidência prova isso?"). Sem prova → marque `NÃO-VERIFICADO` e meça/pergunte. Toda divergência código↔render = **achado**, não correção silenciosa.
- Rode a checagem de contraste (`references/wcag-contrast.py`) nos pares texto/fundo, ícone/fundo, borda e **anel de foco**. Reporte ratios e pass/fail (AA: 4.5:1 texto normal; 3:1 ícone/borda/foco/large text). Desabilitado é isento (WCAG 1.4.3).
- Falha de contraste que **vem do próprio código** (ex.: ícone ativo branco no quadrado #96B4C6 = 2.18:1): **reporte como achado e PARE aí** — não conserte, não sugira correção, não "melhore". Fidelidade ao código é o único objetivo desta skill; a correção é trabalho da skill de auditoria (futura).

## Páginas inteiras (composição) e responsivo
- **⚠️ USE SEMPRE O TEMPLATE `Desktop_layout` — NÃO reconstrua sidebar/top bar.** Toda página web já tem template pronto (sidebar/menu lateral + **top bar** + área de conteúdo com SLOT) e **5 versões responsivas**. Você desenha **só o conteúdo do SLOT**; o chrome e o **espaçamento externo são travados** pelo template — não adicione padding de página. **Receita:** `set = await figma.importComponentSetByKeyAsync('d37b84ba8a84c23291e7ea41959739d33bd0c2e9')` (setKey publicada; ref node `4432:7011` no DS `tRUU84NJUwieOI0A831B8Z`) → `v = set.children.find(c=>c.name==='Property 1=1440')` → `page = v.createInstance()` → `slot = page.findOne(n=>n.type==='SLOT' && n.name==='Content Layout')` → `slot.appendChild(conteúdo)` → `conteúdo.resize(slot.width, conteúdo.height)`. **Larguras do slot:** 1920/1440→1830 · 1024→934 · 768→736 · 390→358. Variantes `Property 1`: 1920/1440/1024/768/390.
- **FLUXO ao terminar o conteúdo — PERGUNTE (AskUserQuestion):** (a) só web · (b) web + todas responsivas · (c) só colocar no template p/ comparar/detectar ajustes. Não presuma. Tendo o template, **não repense o shell** — reuse a instância em todas as versões.
- **Breakpoints = INSTÂNCIAS do componente de página (com slot) em cada largura.** Se há um componente de layout com **slot** (Figma Slot) — ex.: `Desktop_layout` (sidebar fixa + main FILL + `SLOT` "Content Layout"), basta **instanciar e setar a largura** de cada viewport (1920/1440/1024/768/390) que o auto-layout reflui. **Gotcha do slot:** `instance.setProperties({slot: ...})` **FALHA** ("Slot component property values cannot be edited"). Para preencher via plugin: ache o nó `type==="SLOT"` dentro da instância e **`slot.appendChild(contentInstance)`**. **CRÍTICO — slot NÃO faz auto-FILL: ele PRESERVA o tamanho intrínseco do conteúdo.** Então `layoutSizingHorizontal="FILL"` na content costuma NÃO pegar (silencioso) → o conteúdo de largura fixa (ex.: 1334) **transborda e é recortado** em breakpoints estreitos. Fix: **`content.resize(slot.width, content.height)`** por breakpoint, E o conteúdo internamente FILL/grow (filtros, tabela com FILL+minWidth) para reflowar. Sem o resize, parece responsivo mas corta. Nota: layout com sidebar FIXA fica apertado no mobile (390) — o mobile real esconde a sidebar (drawer) e a tabela vira cards; isso vem do código responsivo, sinalize se não lido.
- **Página = composição de INSTÂNCIAS dos componentes já construídos** (sidebar, tabela/Row, status, botões) + chrome (topbar, barra de filtros, paginação). Não redesenhe os componentes — instancie. Tudo em **auto-layout** aninhado: `page = HORIZONTAL [sidebar(FILL altura) + main(FILL)]`; `main = VERTICAL [topbar + content]`; `content = VERTICAL [filtros + tabela + paginação]`. Para um filho usar `layoutSizingVertical=FILL`, o **pai precisa de altura FIXA** (não há `STRETCH` em `counterAxisAlignItems`).
- **Barra de ações (filtros/paginação): `space-between` sozinho CORTA/GRUDA — use grow + HUG + WRAP.** `justify-content: space-between` parece certo mas: se o conteúdo passa da largura, **corta** o cluster da direita; se o pai não está FILL, os dois clusters ficam **adjacentes** (ex.: "193617Itens" grudado). Padrão robusto: cluster **esquerdo `layoutGrow=1`** (empurra o direito pro fim, criando gap real), cluster **direito HUG**, `primaryAxisAlignItems=MIN`, e **`layoutWrap=WRAP`** (em telas estreitas o direito quebra pra baixo, nunca corta). **Inputs (busca): `maxWidth` + `minWidth`** (ex.: 400/220) — FILL mas capado, pra não dominar telas largas nem sumir nas estreitas.
- **Largura fixa VAZA — componentes em container usam FILL/grow (responsivo).** Erro real: tabela com colunas de largura fixa (somando 1356px) **transbordava** o card/página em telas estreitas. O certo é o que o código faz: `width:100%` + colunas com `widthGrow`. No Figma: a tabela = `layoutSizingHorizontal=FILL` do container; cada coluna = `FILL` com `layoutGrow` proporcional (checkbox fixo; Nome `grow 2`; demais `grow 1`); header E linhas com as MESMAS proporções. Assim adapta a qualquer breakpoint (desktop→tablet→mobile) sem vazar. Regra geral: dentro de auto-layout, o filho que deve preencher usa FILL/grow, **nunca** largura fixa maior que o pai.
- **Responsivo do <PRODUTO> (valores reais — não invente):** breakpoint mobile = **`$mediaMobile: 991px`** / `innerWidth <= 990`. No mobile (≤991): **sidebar SOME** (`#sidebar display:none`, `#content-body width:100%`) e vira drawer via hambúrguer; a **`section-header` (barra de filtros) vira `flex-direction: column`** (itens full-width, empilhados); o ícone de recolher é **`text-indent`** (recolhido) / `text-outdent` (aberto) — `eds-button-icon`, NÃO `list-dashes`. **Tabela NÃO vira cards** — colunas têm `min-width: max-content` e a tabela **rola horizontal** (overflow) em telas estreitas. No Figma: colunas = FILL+grow **+ `minWidth`** (não espremer) + card `clipsContent` (overflow = scroll); sidebar `visible=false` nos breakpoints mobile.
- **Slot content é COMPARTILHADO — reflow por largura ≠ reflow por breakpoint.** Auto-layout FILL adapta a largura, mas **não muda `layoutMode`** (ex.: filtros de linha→coluna, paginação que empilha) por breakpoint. Para o mobile real (filtros empilhados, paginação empilhada) precisa de um **componente de conteúdo MOBILE separado** preenchido no slot dos breakpoints ≤991, não dá pra fazer só esticando o desktop.
- **Responsivo (Tablet/Mobile) também é AS-IS:** as versões vêm dos **breakpoints/componentes mobile do código** (media queries, render mobile da tabela — muitas viram cards, sidebar vira drawer), não de invenção. Se não deu para ler o código responsivo, **construa via clone+reflow mas SINALIZE** o que é adaptação (ex.: tabela de largura fixa transborda em telas estreitas; o app real provavelmente rola/vira cards) — e ofereça ler o código responsivo p/ fidelizar. Chrome de app-shell (navbar/footer) que não foi lido a fundo: sinalizar como montado de screenshot+tokens.

## ⚠️ Cores: DOIS sistemas de token — não confundir, não adivinhar
O <PRODUTO> tem **dois conjuntos de tokens** e usá-los trocados é erro de cor garantido:
- **Legado `--ath-color-*`** (escala por nome): `secondary-900 #002a3a`, `secondary-700 #2d3849`, `light #f8f8f8`, `primary-700 #8a76eb`, etc. Usado em componentes antigos (tabela `DataTableCell`, cards, `ath-text-*`).
- **Semântico novo `--content-* / --background-* / --border-*`** (mapeia para `$brand-*`/`$neutral-*`): `--content-primary = $neutral-900 #1a1a1a` (≠ secondary-900!), `--content-brand = $brand-500 #6b55d8`, `--content-primary-inverse = $neutral-50 #f2f2f2`, `--content-disabled = $neutral-300 #b2b2b2`, `--background-brand #6b55d8`, `--background-disabled #f2f2f2`, `--background-hover #f2f2f2`, `--background-selected $brand-100 #e1ddf7`, `--border-focus $brand-600 #5644ad`. Usado no `EdsButton` e componentes novos.
- **Regra:** descubra QUAL token o seletor usa e resolva no sistema CERTO. `content-primary` (#1a1a1a) é texto neutro escuro; `secondary-900` (#002a3a) é o teal escuro. **Nunca** use #002a3a onde o código pede `content-primary`. Na dúvida, `getComputedStyle` do app rodando.
- **Botões = cores POR VARIANTE (não genéricas).** `EdsButton`: primary = bg `--background-brand` + texto `--content-primary-inverse`; **secondary = texto+borda `--content-brand` (brand), bg branco**; tertiary = texto `--content-primary`, bg branco; `filter` = tertiary + borda `--ath-border-color`; disabled = bg `--background-disabled` + texto `--content-disabled`. **NÃO** pinte botão com borda/sec-300 genérico — leia a variante.
- **Inputs/search/pickers: leia o COMPONENTE e seu TEMA — não invente "caixa branca + texto".** Cada campo tem ícone e fundo definidos no código: `NavSearch` = ícone `magnifying-glass` + borda `secondary-300` + radius `--ath-border-radius` (4px); o yearpicker "Ano letivo" usa o tema `AthInputThemeNoBordersLabelSmall` = **fundo `--ath-color-light #f8f8f8` (cinza), radius 10, sem borda** + ícone `calendar-blank`. Erro real: desenhei a busca com elipse genérica e "Ano letivo" como texto solto — faltavam o ícone real e a caixa cinza do tema. Procure o `icon="..."` e o `:theme=...` de cada campo e replique.
- **Backgrounds são EM CAMADAS — não achate tudo numa cor só.** Uma página/tela costuma ter ≥2 camadas: **body/página = cinza** (`--ath-color-light #f8f8f8`) e **superfícies de conteúdo = branco** (`--background-primary #fff`) — cards, painel de conteúdo, topbar, tabela ficam **brancos POR CIMA** do cinza, e o cinza aparece nas margens/gaps. Erro real: pintei a página inteira de `#f8f8f8` (achatado) → sumiu a distinção; o certo é body cinza + **card de conteúdo branco com margem** (o cinza respira ao redor). Identifique cada superfície e sua cor (body vs painel vs card vs header da tabela) — header de tabela é `#f8f8f8` (cinza) DENTRO do card branco. Em auto-layout: body cinza → `contentArea` (transparente, com padding = margem) → `content` (card branco, radius).
- **Renderize o ESTADO que a view mostra.** Erro real: pintei "Matrícula individual" de roxo (primary), mas no tenant **Global** (`!permission.forChangeData()`) o botão está **disabled** (cinza) — é o que o screenshot mostra. Olhe o `:disabled`/`v-if` do contexto e replique o estado real, não o estado "bonito".

## Pitfalls conhecidos (e correção)

- **Conteúdo novo cortado no container externo (overflow do ancestral FIXO).** Ao inserir/expandir conteúdo num auto-layout aninhado (ex.: abrir um submenu), a altura sobe — mas se **qualquer ancestral** na cadeia de layout tiver `primaryAxisSizingMode='FIXED'` (+ `clipsContent`), ele **trunca os irmãos finais** (o último item some — ex.: "Configurações" sumiu quando o submenu cresceu 64px). O frame imediato pode estar HUG e mesmo assim o avô fixo corta. → **Depois de inserir/expandir, percorra a cadeia de pais e garanta HUG (`primaryAxisSizingMode='AUTO'`) em TODOS** (ou redimensione o ancestral para o conteúdo). Corrija na **raiz** (o ancestral fixo/clipado), não só no frame de baixo. Ex. real: `menus` estava HUG (836) mas o componente `Sidebar/Estado=Expanded` estava FIXO 840+clip → setei `AUTO` nele (e no Collapsed) e passou a reffluir (840→924). Nota as-is: em produção o `.menus` tem `overflow:auto` (rola) numa altura fixa; o HUG aqui é conveniência de auditoria (mostra tudo) — sinalize se a fidelidade ao scroll importar.
- **Frame de auto-layout vem com fill branco padrão.** Invisível em card branco, vira "caixa branca" em fundo colorido. → `frame.fills = []` em grupos que não devem ter fundo.
- **Recolor de ícone pinta o container.** Instâncias Phosphor têm uma instância interna com fill + vetores de glifo com **stroke**. → limpe `innerInstance.fills = []` e recolora os `VECTOR` que têm `strokes`.
- **`::before`/`::after` carregam visual ESSENCIAL — vire nó real, não esqueça.** Pseudo-elementos no CSS muitas vezes SÃO o conteúdo-chave: o **check do checkbox** (`&:checked::before` = quadrado 0.9rem radius 0.3rem `--background-brand` #6b55d8 dentro do box `--background-selected` #e1ddf7), os **dots de status** das `label-status-*` (`::before content:'\fXXX'` = glyph Phosphor colorido), ícones de badge, etc. Ao replicar um estado, **procure `::before`/`::after` no seletor** e crie o nó correspondente (frame/vetor/instância). Erro real: no checkbox Selected pintei só o box e esqueci o quadrado interno do `::before` → "perdeu o check". Estado checked/selected sem o seu pseudo-elemento = incompleto.
- **NUNCA use caractere de texto como ícone** (`v`, `⌄`, `‹`, `›`, `x`, `→`…). Todo ícone é uma **instância do componente Phosphor real**. No código aparecem como `<em class="ph ph-caret-left" />` ou `icon="caret-down"` — procure-os e instancie o componente certo (`caret-down`/`caret-left`/`caret-right`/`x`/…). Erro real: select "50" com texto "v", "Mais ações" com "⌄", e setas ‹/› ausentes na paginação (no código: `ph-caret-left`/`ph-caret-right` + "Primeira"/"Última"). Glyph de texto ≈ parecido NÃO é o ícone — quebra a auditoria e fica torto.
- **`resize()` NÃO escala o stroke → ícone/ilustração grande fica "fino".** Ao redimensionar um ícone vetorial (ex.: ilustração de fundo `student` a `font-size:11`/~100px), `resize()` escala a geometria mas mantém o `strokeWeight` original (ex.: 1.5px) → o traço fica fino demais (1.5% do tamanho em vez de ~6.25%). → **Use `node.rescale(factor)`** (escala geometria E stroke) **OU** ajuste `strokeWeight` proporcionalmente: **Phosphor regular = 6.25% do tamanho** (`stroke = size × 0.0625`; base 24px↔1.5px). Ex. real: student a 100px precisa stroke **6.25**, não 1.5. (Ícones pequenos ~20–24px não sofrem; o problema aparece em ampliações grandes.)
- **`resize(w,h)` DEPOIS de setar sizing mode RESETA o mode para FIXED → auto-layout colapsa.** Erro real: cards/hero com `primaryAxisSizingMode='AUTO'` (hug altura) + depois `resize(240,10)` → altura travou em 10px (conteúdo sumiu). Regra: **`resize()` ANTES** de `counterAxisSizingMode`/`primaryAxisSizingMode`, OU re-setar o mode logo após o resize. Padrão "largura fixa + altura hug": `resize(w,100)` → `counterAxisSizingMode='FIXED'` → `primaryAxisSizingMode='AUTO'`.
- **`layoutGrow` exige INTEIRO — float lança erro.** `Property "layoutGrow" failed validation: Expected integer, received float`. Para colunas proporcionais (ex.: tabela col spans 1.5/1.2/2), **escale para inteiros** (×2 → 3/2/4…). O `use_figma` é atômico: o erro aborta o script inteiro (nada é criado) → corrija e rode de novo.
- **Eixos de sizing do component set.** Em auto-layout HORIZONTAL: `primaryAxisSizingMode` = largura, `counterAxisSizingMode` = altura. Para `WRAP`: largura `FIXED` + altura `AUTO`. `resize()` ANTES de setar os modos.
- **`layoutSizing FILL/HUG`** só vale depois de `appendChild` no pai auto-layout.
- **Texto que quebra**: `textAutoResize='HEIGHT'` + largura explícita/`FILL` (após append). Verifique `width > 0`.
- **Anel de foco invisível**: não use uma cor a um passo do fundo (Brand/600 sobre Brand/500 = 1.39:1). Garanta ≥3:1; muitas vezes o anel sobre fundo branco resolve.
- **Mudar `characters`/fonte exige `loadFontAsync` + `await`.** Só mudar `fills` não exige.
- **PREFLIGHT DE FONTE (Satoshi) — OBRIGATÓRIO ao instanciar/editar texto de componente do DS.** Os componentes do DS foram autorados em **`Satoshi Variable`**, que **NÃO carrega no connector** (`loadFontAsync({family:'Satoshi Variable'})` é rejeitado) — só a **`Satoshi` estática** existe/está instalada, e é o que o **CÓDIGO usa** (`SatoshiRegular/Medium/Bold`). Sem o preflight, o **próprio `appendChild`** de uma instância lança `unloaded font "Satoshi Variable Medium"` (e `setProperties` de label idem). **Receita:** (1) `await figma.loadFontAsync({family:'Satoshi', style:'Medium'})` (+ Bold/Regular conforme o peso); (2) `createInstance()`; (3) **ANTES de `appendChild`**, troque a fonte de TODOS os text nodes p/ estática: `inst.findAll(n=>n.type==='TEXT').forEach(tn=>{ tn.fontName={family:'Satoshi', style: tn.fontName.style} })`; (4) `appendChild` → `setProperties({'Texto#1104:6': label, ...})`. Mapa de peso: Variable `Medium/Bold/Regular` → `Satoshi/Medium|Bold|Regular`. **Causa-raiz:** a **lib PUBLICADA está desatualizada** (snapshot Variable de 2026-04-14); o DS **local** já está em Satoshi estática (18 text styles + nós migrados). Quando a lib for **republicada** (ação de UI do Paulo: Assets → Publish), o `importComponentSetByKeyAsync` passa a servir estática e o swap deixa de ser necessário — **mantenha o preflight como rede permanente**. Memória: `ds-button-satoshi-variable`.
- **Imagens reais (logos/PNG): use o tool `upload_assets`, não `use_figma`.** No `use_figma` não há `fetch`/`XMLHttpRequest` e `createImageAsync(url)` lança "not a supported API"; base64 grande corrompe. → Crie um RECT do tamanho certo, pegue o id, e chame `mcp__claude_ai_Figma__upload_assets({fileKey, nodeId, count:1, scaleMode})` → POSTe o arquivo real via `curl -F "file=@.../logo-primary.png;type=image/png" "<submitUrl>"`. Embute o asset EXATO, sem transcrição (PNG/JPG/GIF/WebP, ≤10MB; SVG → `createNodeFromSvg`). Stand-in colorido é só último recurso, sempre com a **cor real** do asset. Ver `references/figma-snippets.md`.
- **Estado ativo: valide qual sub-elemento recebe qual cor.** Foi onde mais errei — confira no print de produção que label, ícone e fundo do item ativo batem (label costuma ser clara/branca; o quadrado do ícone é o accent).
- **`node.clone()` NÃO garante virar irmão do original no `use_figma` — confirme o `parent` antes de seguir.** A doc oficial do Plugin API diz que o clone é inserido logo depois do nó original, no MESMO pai; na prática (via `use_figma`), um clone de uma célula dentro de uma linha de auto-layout aninhada apareceu com `parent.id` = **página raiz** (`0:1`), não a linha esperada — a tabela ficou visualmente idêntica ao "antes" (mesmo hash de screenshot) porque o clone nunca chegou lá. Causa provável: quanto mais fundo o nó clonado está na árvore (linha dentro de tabela dentro de card dentro de frame), menos confiável fica a heurística de "sibling automático". **Depois de todo `clone()`, leia `clone.parent.id` no retorno do script e compare com o pai esperado** — se divergir, reparente na mesma chamada (ou numa seguinte) com `esperadoPai.insertChild(indiceOriginal + 1, clone)`. Não confie que "o script não deu erro" = "o clone está no lugar certo": sem esse cheque, o build inteiro (14 nós) foi criado "com sucesso" e ficou invisível. Ex. real: coluna nova "Novo componente" na tabela de Migração do painel-eficiencia (2026-07-25).
- **Clonar uma célula de texto pra um valor MAIS LONGO que o original quebra linha se o texto for `textAutoResize:'HEIGHT'` (largura fixa herdada do clone).** Ao clonar a célula "Componente" (texto "Componente", ~86px) pra virar o header "Novo componente" (mais longo), só troquei `characters` — o node de TEXTO manteve a largura antiga (86px, herdada do clone) e o texto quebrou em 2 linhas dentro dela, mesmo com a CÉLULA (frame-pai) já redimensionada pra 280px. Sintoma: só o header quebra, as células do corpo (que reusam o MESMO texto do original, ex. "EdsInputSelect"→"EdsInputSelect") não quebram — porque nelas o conteúdo não mudou de tamanho. **Regra: ao reaproveitar/clonar um nó de texto pra um valor de tamanho diferente, ajuste também a largura do TEXTO** (não só do frame-pai) — `text.textAutoResize = 'WIDTH_AND_HEIGHT'` deixa recalcular sozinho (`width`/`height` viram os do novo conteúdo, 1 linha), ou `text.resize(novaLargura, altura)` mantendo `'HEIGHT'`. Ex. real: mesma coluna "Novo componente" acima.

## Princípios de arquitetura aplicados (DDD + Clean Architecture)
> Extraídos dos livros **só** no que aumenta eficiência/fidelidade desta skill (o resto — camadas, use cases, entities/services, versionamento de release — foi descartado de propósito).

- **Linguagem Ubíqua (DDD) → paridade de nomes.** Use no Figma EXATAMENTE o vocabulário do código: nome do componente = nome do SFC (`MenuItem`); eixos/valores de variante = props/estados do código (`State=Default/Hover/Active`, `Layout=Expanded/Collapsed`); nomes de layers ≈ estrutura do template; variáveis = nomes semânticos dos tokens. Nome divergente quebra a auditoria e gera adivinhação/retrabalho.
- **Bounded Context + Anti-Corruption Layer (DDD) → traduza cada componente do SEU código; isole o externo.** Nunca importe o modelo de outro componente/lib para tapar lacuna (ex.: o `Card - Button` ou a lib antiga "Case <EMPRESA>") — isso "corrompe" a réplica (foi a raiz das falhas de contraste e da divergência de estados). Se precisar referenciar algo externo, trate como contexto separado; só os ícones oficiais entram como dependência.
- **Conformist vs. Anti-Corruption (DDD) → distinga "reusar o oficial" de "deixar vazar um modelo divergente".** A lib oficial do DS no Figma é um *upstream* que você não controla: com ela seja **Conformist** — reuse a instância **as-is** (ícones, subcomponentes oficiais), sem reestilizar/forkar. Já um componente que **diverge** do código que você replica é o caso de **Anti-Corruption**: isole, não deixe o modelo dele entrar. ("When two teams with an upstream/downstream relationship are not effectively directed from the same source… the downstream team conforms.")
- **Coesão de componentes — REP/CCP/CRP (Clean) → regra de granularidade.** Vire componente o que é **reusado como unidade** (REP: `MenuItem` usado 14× → componente; decoração única → inline). Agrupe no MESMO componente o que **muda junto** (CCP: ícone+label+estados do item). Não empacote variantes/props que o item **não usa** (CRP) — exatamente o "só os estados que o código tem".
- **Aggregate + SRP (DDD/Clean) → fronteira de composição; 1 componente = 1 unidade do código.** O container é um *aggregate* que possui seus sub-componentes (`Sidebar` → instâncias de `MenuItem`); o uso externo referencia a **raiz** (o componente), não partes internas. Cada componente tem uma só razão para mudar — não achate responsabilidades no container.
- **Regra da Dependência / abstrações estáveis (Clean) → dependa de tokens estáveis.** O desenho concreto depende das variáveis semânticas (camada estável), nunca de hex hardcoded — assim a dependência aponta para o estável e mudanças no DS propagam.
- **Value Object (DDD) → token é valor imutável e compartilhável: VINCULE, nunca copie o hex.** O próprio livro usa **cor** como exemplo de Value Object: *"Colors are an example of VALUE OBJECTS… Treat the VALUE OBJECT as immutable… Immutable objects can be freely shared."* Um token não tem identidade própria — é definido pelo valor. Logo, no Figma aponte para a variável (`setBoundVariableForPaint`) em vez de "carimbar" o hex resolvido; copiar o valor cria uma cópia órfã que não acompanha o DS (é o reforço concreto da regra de ouro 3 e da Regra da Dependência).
- **Model-Driven Design + Continuous Integration (DDD) → uma réplica única, sempre re-derivada do código ATUAL.** *"This binding of model and implementation… ensures the analysis applies to the final product."* O Figma é o modelo; o código é a implementação — eles têm de ficar amarrados. Por isso: rode `<produto>-sync` e releia o SFC/SCSS a cada build (não confie em memória/versão antiga); mantenha **um** componente canônico (não forks/cópias paralelas); e trate qualquer divergência Figma↔código como *"splinter"* (sinal de que o modelo se fragmentou) a reportar — não a tolerar.

## Lições de produção (registradas após divergências reais)
1. **Mapear seletores compostos com precisão.** No sidebar, a label ativa é `$color-text-active` (#F8F8F8, branca), NÃO `$color-active` (#96B4C6, que é só o `>a`/borda). Confundir sub-elementos do estado ativo foi a falha mais comum → use a tabela `{sub-elemento → propriedade → var}`.
2. **Asset = cor real, sempre.** O logo do app é o wordmark **roxo (brand)** + mark roxo com "e" branco. Placeholder branco foi adivinhação. Embuta o asset real (`createImageAsync` via server local) ou, se impossível, placeholder com a **cor de marca correta** e sinalizado.
3. **Validar contra produção antes de fechar.** Vários erros (logo, label ativa) só apareceram quando comparei com o print de produção. Sempre buscar/pedir um print real e comparar lado a lado.
4. **Não esqueça os SUB-COMPONENTES e seus ESTADOS.** Erro real: construí o `Sidebar` (variantes Collapsed/Expanded) mas esqueci o `MenuItem` com seus estados. Para cada SFC importado, crie um component set próprio com os estados que o **CSS realmente define** — nem mais, nem menos. Ex. `MenuItem` (de `_sidebar.scss`): **Default**, **Hover** = `:hover { opacity: var(--ath-opacity) }` (0.6), **Active** (rota selecionada) = quadrado #96B4C6 + ícone branco + label #F8F8F8 + borda-esq 3px. **NÃO** tem `:focus`/`:active`(pressed)/`:disabled` no código → não invente esses (se o usuário pedir um estado inexistente, avise que não está no código e pergunte se quer um deliberado, fora do as-is).
5. **Imagens reais: tool `upload_assets` + curl** (não `createImageAsync`/base64). Crie rect, `upload_assets({nodeId})`, POSTe o arquivo. Ver `references/figma-snippets.md`.
6. **Container = INSTÂNCIAS do sub-componente, não filhos achatados.** O serviço só está completo quando o container (ex.: `Sidebar`) usa **instâncias** do sub-componente (ex.: `MenuItem`) — assim cada item carrega seus estados. Por instância: `swapComponent(iconComp)` para o ícone certo + **recolor DEPOIS do swap** (o swap traz a cor original), `characters` para o label, e elementos opcionais (tag) via **`visible`** (inclua-os no componente, ocultos por padrão).
7. **Componente que muda por contexto = eixo de variante extra.** Se o mesmo componente renderiza diferente conforme o container (ex.: `MenuItem` Expanded com label vs Collapsed icon-only — no código a label é escondida via `template{display:none}`), modele como **2 eixos no MESMO set**: `Layout=Expanded/Collapsed` × `State=...`. Anexe componentes nomeados `Layout=X, State=Y` ao set (`set.appendChild(comp)`); o set passa a expor as duas propriedades.
8. **Componentes RECURSIVOS / com sub-itens expansíveis: mapeie a árvore inteira — não pare no item "folha".** Erro real: construí o `MenuItem` só como item plano (Default/Hover/Active) e **esqueci o ramo de submenu**. No código, o `MenuItem` é **recursivo** (`<menu-item v-for="submenu in props.subMenus">` dentro dele) e renderiza um container condicional. Sinais no template a procurar SEMPRE: prop tipo `subMenus?: T[]`, flag `hasSubMenu`/`isSubMenu`, `v-if` de um container aninhado, ícone indicador (caret). Ao achar isso, modele os **três** elementos que faltam:
   - **(a) Indicador de expansão no item-pai.** `MenuItem` com `subMenus` mostra um caret: `caret-right` (fechado) / `caret-down` (aberto). → propriedade nova, ex.: `Submenu=None / Collapsed / Expanded`.
   - **(b) Container expandido como elemento próprio, com SEUS tokens.** `.submenu-container`: `background:#96b4c6` (`$bg-submenu`), `border-radius:var(--ath-border-radius)`, `margin:0 0.4rem`; cada `li` interno `padding:10px 0`. Não é "o mesmo fundo do item" — é um bloco distinto.
   - **(c) Sub-item é uma VARIANTE distinta (`isSubMenu`), com estados próprios ≠ do item principal.** Ícone menor (`font-size:1.5` vs `2.4`, classe `icon-submenu`); label `secondary-700` (vs `secondary-400` no principal); **ativo** = quadrado de ícone **branco** (`$color-icon-active`) + ícone `#96b4c6` + label `secondary-900` — exatamente o INVERSO do ativo do principal (quadrado `#96b4c6` + label/ícone brancos). Ex. real: "Integração" (`arrows-in-line-vertical`) → "Remessa" (`arrow-fat-line-up`) + "Retorno" (`arrow-fat-line-down`).
   Em Figma: o container instancia **instâncias do sub-item** (recursividade do código → instâncias aninhadas), nunca filhos achatados (reforça a Lição 6).
9. **Reproduza o COMPORTAMENTO, não só o visual — componente interativo.** Erro real: na 1ª passada deixei o submenu como montagem **estática** (item Integração + container soltos no Sidebar). O código tem `subMenuOpened` que **expande/recolhe no clique, dentro do próprio item** — então o Figma tem de fazer o mesmo na instância. Receita:
   - **Eixo de variante por estado interativo:** ex. set `MenuItem - Integração (submenu)` com `Submenu=Collapsed` (caret-right, sem container) e `Submenu=Expanded` (caret-down + container). O submenu vive **dentro** do componente.
   - **Reação de protótipo:** na linha-pai de cada variante, `node.setReactionsAsync([{ trigger:{type:'ON_CLICK'}, actions:[{type:'NODE', destinationId:<outra variante>, navigation:'CHANGE_TO', transition:{type:'SMART_ANIMATE',easing:{type:'EASE_OUT'},duration:0.25}}] }])`. Assim a **instância** alterna sozinha no modo apresentação — recolhe/expande o submenu, **sem** mexer no resto da sidebar.
   - **Caret por estado:** Collapsed = `caret-right`, Expanded = `caret-down` (swap do ícone do caret por variante).
   - **Gotcha de layout:** a instância do grupo no container pai (auto-layout) precisa de `layoutSizingVertical='HUG'` — senão fica presa na altura-base do componente (ex.: 10px) e o conteúdo some.
   - Sizing de variante interativa: ambas as variantes com `primaryAxisSizingMode='AUTO'` (hug vertical) para acomodar o container que aparece/some. **Atenção ao clonar:** o clone herda a altura-base FIXED — re-set `AUTO` em cada variante criada por `clone()`.
   - **Generalize como família reutilizável, não como one-off.** O componente é `MenuItem - Submenu` (genérico: ícone trocável, label editável, sub-itens como instâncias), não "Integração". A instância na sidebar é Integração via override.
   - **Cruze com o modo da sidebar (2 eixos): `Sidebar=Expanded/Collapsed × Submenu=Collapsed/Expanded`** (4 variantes). O toggle de clique alterna **só** o eixo `Submenu`, **mantendo** o `Sidebar` — recolher/expandir o submenu nunca recolhe a sidebar.
   - **Modo Collapsed (icon-only) é AS-IS pelo CSS:** em `.active-sidebar`, `template{display:none}` esconde **label E caret** (o caret vive dentro do template) → no Figma, sem label/caret nas variantes Collapsed. O `.submenu-container` continua `#96b4c6` mas a 58px com os sub-itens **só-ícone** empilhados (labels também escondidas). Não invente flyout/hover-popover se o código renderiza o submenu inline.
   - **Estado ativo do sub-item NO collapsed também existe** (`.active-sidebar … .submenu-container li span .active`): ícone numa **caixa branca** (radius 3, padding 5) + ícone `#96b4c6` (`$color-active`), só-ícone — mesmo tratamento do ativo expandido, sem label. Modele como set próprio `Submenu Item - Collapsed` (State=Default/Active, ícone trocável). Contraste ícone ativo `#96b4c6`/branco = 2.18:1 → achado as-is (não corrigir).
10. **Ausência de algo (ícone/estado) pode ser AS-IS — confira o mapa/código antes de "corrigir".** Apontado como bug: "a variante Canceled não tem ícone no círculo". Logo o vazio é **fiel**, não defeito (e `styleEnrollmentStatus` tem `Canceled:grey` → cor sim, ícone não). Regra: quando algo "parece faltar", **verifique no objeto/map do código** que resolve aquele valor. **Não invente** o que falta; reporte como as-is. Se o usuário insistir num ícone inexistente, é **deliberado/não-código** → **PERGUNTE qual** (não dá para adivinhar o glifo certo).
11. **Se a tela já existe como componente/mock da lib no arquivo, CLONE e refine — não remonte do zero.** Antes de construir uma tela, verifique se ela (ou o container dela) já existe montada no arquivo Figma (a equipe de design costuma ter o modal/página feito com a lib). Se existe: `node.clone()`, mova pro frame alvo e **edite cirurgicamente** — (a) trocar os dados/textos pelo estado do código/screenshot; (b) reconstruir **só as seções que divergem** da versão atual. Caminho mais rápido e mais fiel à lib (Conformist). Ex. real: "Modal | Atualização de faturas" já existia numa versão antiga; clonei e só refiz o painel direito (Item da fatura #1, Aplicar encargos, textarea Motivo da atualização, Total) + atualizei o header. **Corolário — RENDER É A FONTE quando o ambiente diverge do código:** o build do dev/homolog pode estar à frente/atrás de `develop`; nesse caso o **screenshot renderizado é a verdade** do estado a desenhar (render computado > SCSS > suposição) — replique o screenshot e **sinalize** a divergência de versão em vez de "consertar" pro que o `develop` diz. **Estados `:hover`/`:active` capturados no screenshot são as-is** (ex.: `AthCard` com card em hover `#6b55d8` + card active `#2b2256`, os dois visíveis no mesmo print → replique ambos). Técnica: recolorir ícone Phosphor dentro de instância = trocar `strokes` (e fills, se houver) dos `VECTOR` internos (`findAllWithCriteria`); override de fundo do card = setar `instance.fills` mesmo com o branco vindo do master; editar texto dentro de instância exige `loadFontAsync` do fontName atual antes de `characters`; `setRangeFills` p/ colorir só parte do texto (ex.: "#1" mais claro).

12. **Fluxo multi-step (wizard) = N telas, uma por `currentStep`; o stepper é um componente com estado por etapa.** Ao replicar um fluxo (ex.: criação de fatura = `CreateInvoiceNew.vue` → `AthModal type="right"` + `AthWizard` + `v-if currentStep===n`), desenhe **uma tela por etapa** do wizard, cada uma no estado real daquela etapa. Elementos que mudam por etapa: (a) **título** do header = `steps[currentStep-1].label`; (b) **stepper** — cada passo é um círculo 33px com 3 estados no CSS do `AthWizard`: **active** (borda+dot+label `primary-700 #8a76eb`, fundo transparente), **finished** (fundo+borda `success #2ecc71` + ícone `check` branco + label verde), **future/disabled** (borda+label `#cccccc`); o `●` do active é um **dot** (ellipse), não caractere; o check do finished é o ícone Phosphor real; (c) **footer** — botões mudam por etapa (`v-if currentStep===1` → "Cancelar"; senão "Voltar" com `caret-left`; última etapa → "Gerar fatura", senão "Avançar" com `caret-right`; primary tem `width="flex"` → `layoutGrow`). **Técnica eficiente:** construa a 1ª tela inteira (drawer chrome + wizard + body + footer), valide, e **clone o drawer** para as demais, refazendo só título+wizard+footer+body (Lição 11 aplicada ao fluxo). **Composição da tela (modal drawer sobre lista):** reuse a tela de fundo já pronta da lib (clone do frame da lista) + **backdrop scrim `rgba(51,51,51,0.5)`** (`.modalVue__backdrop`) + **drawer** `type="right"` (col-md-8 ≈ 66% da largura, encostado à direita, `box-shadow 0 4px 8px rgba(0,0,0,.2),0 6px 20px rgba(0,0,0,.19)`) + **botão de fechar** = círculo 50px branco, borda **7px `#949494`**, `left:-30px top:26px`, ícone `x`. **Grid `col-N` com `v-if` no FILHO (não no `col`):** o `<div class="col-6">` fica SEMPRE no DOM; só o input interno some com `v-if` — então as colunas vazias **colapsam mas mantêm a posição do grid** (ex.: em "Geração de faturas" sem escola, "Empresa" cai na coluna DIREITA porque os `col-6` de Curso/Turma/Matrículas vazios ocupam os slots anteriores). Leia se o `v-if` está no col ou no filho antes de posicionar. **Accordion `AthAccordion`:** o caret só renderiza com `activeClick && showArrow` — `active-click="false"` (ex.: "Informações escolares") ou `show-arrow="false"` (ex.: "Tipo de cobertura") → **sem caret**; header bg = `primary-50 #f3f1ff` (headColor, NÃO alterado por `bg-color`). **Achados as-is (contraste, do próprio código, não corrigidos):** tag "Receita garantida" `#8a76eb/#f3f1ff` = 3.21:1; label ativo do wizard `#8a76eb/#fff` = 3.58:1; check verde `#2ecc71/#fff` = 2.10:1; borda de input `#b2b2b2/#fff` = 2.12:1 — todos <mínimo, reportados. (Label de etapa futura `#cccccc` = 1.61:1 é **isento**: estado disabled/inativo.)

13. **TOKEN vinculado ≠ valor cru — e o SISTEMA certo importa (legado × novo).** O entregável não pode ter cor/tipografia hardcoded: todo fill/stroke deve ser **paint style ou variável**, e todo texto um **text style**. Ao selecionar o nó, o painel tem de mostrar o token (não `002A3A`/`Satoshi 24` cru). **Regra dura — DOIS sistemas coexistem; decida POR COMPONENTE, não por tela.** O <PRODUTO> usa os dois sistemas ao mesmo tempo (medido: 79 arquivos novos, 324 antigos, **43 misturam**; ex.: `EdsButton` usa `--background-brand`/`--content-primary` NOVOS **e** `--ath-color-*` ANTIGOS no mesmo arquivo). **Numa mesma página, cada componente pode estar num sistema diferente — e um componente pode misturar.** Para CADA nó/propriedade, leia o código do componente que o renderiza e classifique: **NOVO** (`var(--content-*)`/`var(--background-<role>)`/`var(--border-<role>)`/`var(--eds-*)` ou componente `eds-*`; defs em `themes/root.scss`) → **variáveis `Semantic:Color`** + text styles `Type/EDS_*`; **ANTIGO** (`var(--ath-color-*)`/`ath-text-*`/`Ath*`/custom) → **paint styles do 💜** (`secondaryColor/*`,`semanticColor/*`,`surfaceColor/*`,`primaryColor/*`) + `Satoshi/*`. **Misturar na mesma tela é fiel** (é o que o código faz). ⚠️ Vincular ao sistema errado **muda a cor** (secondary-900 #002a3a ≠ Content Primary #1a1a1a; danger #e50000 ≠ #eb5757). ⚠️ **CSS var local disfarçada** (`--border-color`/`--bg` no próprio `<style>`) NÃO é token DS — resolva até a origem antes de classificar (ex.: `AthCardButtonSimple` tem `--border-color` local mas é **todo legado**). **No passo 3 (spec) registre, por elemento, o sistema de token** (coluna "sistema: novo/antigo") junto com a var — vira o mapa de vínculo. **Método** (`importStyleByKeyAsync(key)` → `setFillStyleIdAsync/setStrokeStyleIdAsync`/`setTextStyleIdAsync`; keys no `figma-ds-reuse-map.md` → "Estilos legados 💜"): num arquivo de trabalho as libs só aparecem no picker **depois de usadas** — importar+aplicar por key resolve. **Onde o DS não bate o valor do código** (drift real: danger #e50000, warning #efca44, warning-dark #c5a533) → **crie paint style LOCAL `<PRODUTO>/código/*`** com o hex exato (fiel + tokenizado), não deixe cru. **Tipografia:** só há a grade Satoshi xs=12/sm=14/md=16/lg=20/xl=24 → **snap** 18→16, 11→12. **Pode construir com hex e fazer um "rebind pass" no fim** (andar `root.findAll`, mapear hex→style pela cor REAL resolvida, aplicar) — testado: 106 fills+59 strokes+63 textos, 0 falhas, até em vetores de ícone dentro de instâncias. **Gotcha:** nó com **variável** vinculada resolve p/ o valor DELA (Content Primary→#1a1a1a) e não casa no mapa de hex do código → limpe `fills[0].boundVariables={}` antes de aplicar o estilo legado. **Números (radius/spacing/padding/border) também são token:** `node.setBoundVariable(field, await figma.variables.importVariableByKeyAsync(key))` — coleção `Global tokens` (Radius/Spacing px; keys no reuse-map). Campos: 4 cantos p/ radius uniforme; `itemSpacing`; `padding*`; `strokeWeight` (uniforme grava os 4 lados; borda de 1 lado = `strokeBottomWeight`). Escala DS termina em 26 → valores fora da grade (1/5/6/28/32…) NÃO têm token → **variável LOCAL** `<PRODUTO> código (números)` (`createVariable` FLOAT).

15. **Frame no Figma NASCE BRANCO — limpe o fill dos wrappers ou eles viram "caixas" indevidas.** Divergência real (redesign do Gerenciador de documentos, node `145:583`): stepper, intro (título+subtítulo), reforço e footer saíram com `bg-white` sobre o fundo cinza da página, criando containers brancos e emendas cinza entre as seções — só os DocContainers deviam ser cards brancos. **Causa:** no Figma o fill default de TODO Frame é **#FFFFFF sólido a 100%** — diferente de um Group (transparente) e do `<div>` HTML/CSS (transparente). 16. **3 pitfalls de `use_figma` que se repetem em builds de PÁGINA (não só componente) — checklist antes de rodar cada script.** (a) **`resize()` depois de setar `primaryAxisSizingMode`/`counterAxisSizingMode` reseta pra FIXED silenciosamente** — se o container precisa ficar `AUTO` (hug), re-sete o modo DEPOIS de qualquer `resize()` seguinte, mesmo que pareça inofensivo (o sintoma é conteúdo cortado numa altura suspeita tipo 400, sem erro nenhum — só se percebe comparando `content.height` retornado com a soma manual dos filhos). (b) **`node.appendChild(child)` retorna `undefined`** — nunca encadeie `.layoutSizingHorizontal='FILL'` direto no retorno (`parent.appendChild(x).layoutSizingHorizontal=...` lança erro num `null`); separe em duas linhas ou use um helper `appendFill(parent,node){parent.appendChild(node); node.layoutSizingHorizontal='FILL'; return node;}`. (c) **`use_figma` é ATÔMICO — um erro na PARTE FINAL de um script descarta TUDO que o mesmo script já tinha construído antes**, mesmo que essa parte anterior parecesse ter "funcionado". Erro real: script construiu panel-head + card-resumo + tabela; o erro foi só na tabela (ordem `appendChild`/`FILL` errada); resultado: a tela ficou SEM NADA, nem o header nem o card — só percebido no screenshot da correção seguinte (mostrava a tabela sozinha, sem o resto). Depois de corrigir um erro parcial, **reconstrua também as partes anteriores do mesmo script** — elas nunca existiram de fato no arquivo. Prevenção: para telas grandes, prefira MAIS chamadas menores (1 seção por chamada) a menos chamadas grandes, mesmo que pareça mais lento. (2026-07-25, réplica das 9 telas do painel-eficiencia)
17. **Dois limites DISTINTOS do Figma MCP — não confundir.** (a) **Tamanho de resposta por chamada** (`get_metadata` de uma página inteira estoura tokens) → contornável lendo o arquivo salvo (`/tmp/...txt` que a tool devolve) com `grep`/`jq` pelo nome do frame, sem paginar a árvore toda (ver Pitfall #11 do `figma-ao-codigo.md`). (b) **Cota de chamadas do PLANO** ("limite atingido no seu plano — Full seat, Professional") — aparece de repente no meio de uma tarefa (ex.: depois de 1 `get_metadata` grande + 1 `whoami` + 1 `get_screenshot`), e **não é contornável**: repetir a chamada não resolve, só gasta mais uma tentativa contra o mesmo teto. Ao bater em (b): **pare de chamar tools do Figma imediatamente**, reporte objetivamente o que já foi feito/achado até ali, e pergunte ao usuário como seguir (aguardar o reset vs. resolver plano/seat) — nunca insista tentando de novo. (2026-07-25, página Qualidade do painel-eficiencia)

Achado real: pedido verbal foi "cards coloridos por gravidade + tag colorida na tabela"; implementei a interpretação mais rica (fundo tingido no card, pill colorido na tag) sem olhar o Figma primeiro — ao entrar pra replicar, a tela já tinha esse resumo redesenhado pelo próprio usuário, com um estilo mais sóbrio (card branco neutro, cor só no dot, nunca no fundo/texto) e cores vinculadas a variáveis reais do DS que não bati de primeira (chutei tons mais escuros que a variável real). Tive que reimplementar o CSS/JS duas vezes. **Regra:** antes de escrever qualquer CSS/JS a partir de uma descrição verbal de estilo, se a tela-alvo já existe no Figma, faça 1 `get_metadata`/`get_screenshot`/leitura de `fills`+`boundVariables` PRIMEIRO — o código só deve nascer depois de conferir o que já foi desenhado, não em paralelo/antes.

20. **Cadeia `layoutSizingHorizontal` FILL vs HUG em auto-layout aninhado — um elo em FILL trava o crescimento de TODOS os ancestrais acima.** Ao editar um pill/célula pra caber texto mais longo, não basta setar `primaryAxisSizingMode='AUTO'` (hug) no frame mais próximo do texto — se QUALQUER elo intermediário da cadeia (texto → wrapper → pill → coluna → row) tiver `layoutSizingHorizontal='FILL'` (herdado do desenho original, pensado pra um conteúdo mais curto), esse elo trava sua própria largura independente do pai estar em hug, e o crescimento não se propaga pra cima — sintoma: texto com `textAutoResize='WIDTH_AND_HEIGHT'` continua cortado visualmente, mesmo com o frame imediato "certo". **Antes de mexer num pill/coluna que precisa crescer, percorra a cadeia INTEIRA de ancestrais e garanta consistência**: cada nível = `layoutSizingHorizontal='HUG'` (como filho) + `primaryAxisSizingMode`/`counterAxisSizingMode='AUTO'` (como frame, no eixo certo conforme seu `layoutMode`) — não só o nó mais próximo do texto. Ex. real: pill de agente no painel-eficiencia (`Construtor do Storybook`) só cresceu depois de corrigir `nameWrap` (FILL→HUG), `agent` (AUTO), `jcards` (counterAxisSizingMode AUTO + HUG), `jcol` (HUG) e por fim a `journey` row (`primaryAxisSizingMode='AUTO'` pra não clipar a soma das colunas agora mais largas). (2026-07-26, redesign do Hub de Design)

21. **Barra "2 filhos lado a lado" (fill + espaçador transparente) — não assuma qual filho é o visível pela posição.** Padrão de barra mais comum é 1 fill colorido DENTRO de 1 track cinza (2 nós, um pai-filho). Mas um padrão alternativo real (visto no painel-eficiencia) é 2 FRAMES IRMÃOS lado a lado somando 100% da largura: `children[0]` = o retângulo com `fills` de verdade (a cor visível), `children[1]` = um espaçador com `fills: []` (transparente, só ocupa o resto). Redimensionar o filho errado (por achar que "o segundo é o track cinza de fundo") produz uma barra que **parece** normal no screenshot mas mostra `100−pct` em vez de `pct` — bug silencioso, só visível comparando o valor numérico da largura contra `trackW × pct/100`, não pela imagem. **Antes de redimensionar qualquer filho de uma barra de progresso, leia `fills` de cada um** — o que tem `fills` não-vazio é o que carrega o significado visual; nunca assuma pela posição/nome genérico ("Frame"). (2026-07-26, auditoria pós-entrega do redesign do Hub de Design)

22. **Instância de componente NÃO aceita `appendChild` de nó novo — suba pro pai pra "colar" algo do lado de fora da árvore da instância.** `sidebarInstance.appendChild(rect)` lança `Error: Cannot move node. New parent is an instance or is inside of an instance` mesmo que o rect deva ficar visualmente "grudado" na instância (ex.: indicador de estado ativo que depende de qual item está selecionado NAQUELA tela, então não pode ser bakeado no componente mestre). Solução: adicione o nó ao **pai** da instância (ex.: o `Row` que contém `Sidebar`+`Content`), com posição absoluta calculada em coordenadas do pai (`instance.x + offsetInterno`), e marque `layoutPositioning='ABSOLUTE'` se o pai for auto-layout. (2026-07-26, indicador de item ativo da sidebar do Hub de Design)
23. **Ícone sem correspondente exato na lib do DS → trace o path real via `figma.createNodeFromSvg`, não force um ícone "parecido".** Nem toda forma do código tem um Phosphor/lucide oficial já catalogado na lib conectada (`search_design_system` pode não achar nada, ou só achar algo semanticamente plausível mas com traço DIFERENTE — ex.: usei "Plugs" pra um ícone de "Conexões" que na verdade tem o path de uma taça/cálice, não de tomada). Regra: se o `search_design_system` não retornar um componente cujo PATH bate (não só o nome parece fazer sentido), **reconstrua o SVG exato** do código (`viewBox`, `stroke-width`, `stroke-linecap/linejoin` iguais) via `figma.createNodeFromSvg(svgString)`, embrulhe num `figma.createComponent()` (pra virar swappable via Icon#instance-swap), e vincule o `stroke` à variável de cor do ícone (nunca deixe o hex do SVG cru). Mais fiel do que adivinhar por semântica do nome do item de menu. (2026-07-26, 3 ícones da sidebar do Hub de Design)

24. **Reforço real do Pitfall #16 (resize antes do sizing mode) — errei de novo mesmo com a regra escrita.** Ao criar um helper novo rápido (`makeModelBars`, barrinhas de força do modelo na tabela Uso e Adoção), fiz `wrap.resize(3,12)` DEPOIS de já ter setado `primaryAxisSizingMode='AUTO'` — resultado: o wrapper travou em 3px de largura (só a 1ª de 4 barras aparecia, as outras 3 ficaram cortadas fora da área visível). **A regra só protege se virar checklist mental automático em TODO helper novo, não só quando "lembrar dela"**: antes de escrever `resize()`, pergunte "isso vem antes de qualquer `primaryAxisSizingMode`/`counterAxisSizingMode` que eu setei nesse nó?". (2026-07-26, tabela Uso e Adoção do Hub de Design)
25. **"Auditar contra o app rodando" também precisa ir fundo na RENDERIZAÇÃO de dados (`js/app.js`), não só no CSS estático.** Uma auditoria anterior (screenshot vs. screenshot) confirmou números/textos batendo mas não pegou que a tabela inteira estava faltando: ícone por linha, alinhamento numérico à direita, indicador de força do modelo, e larguras de coluna — porque essas 4 coisas só existem na função JS que MONTA a linha (`renderChart()`), não em nenhuma classe CSS óbvia de se grep-ar direto. **Regra: ao auditar uma tabela/lista dinâmica, sempre leia a função JS que gera o `innerHTML`/markup daquela linha inteira (não só as classes CSS de estilo) — é lá que mora a estrutura real (que elementos existem, em que ordem), enquanto o CSS só estiliza o que já foi decidido existir.** (2026-07-26, mesma tarefa)
26. **Auto-layout VERTICAL também ignora `x`/`y` manual (não é só o caso HORIZONTAL já documentado) — a posição real é 100% ORDEM no array `children`.** Ao tentar posicionar um chip novo "ao lado" de um texto existente (mesma linha) e depois reordenar um divisor+bloco pra ficarem ANTES de um filho já existente, setar `node.x`/`node.y` direto **não fez NADA** — os elementos simplesmente empilharam na ordem em que foram `appendChild`ados (que põe sempre no FIM da lista), com o gap fixo do `itemSpacing` do pai. Sintoma: y's "aleatórios" que não batem com nenhuma conta manual de posição. **Diagnóstico rápido: leia `parent.layoutMode` — se for `'HORIZONTAL'`/`'VERTICAL'` (não `'NONE'`), pare de tentar `x`/`y` e resolva com ORDEM.** Fix de 2 partes: (a) **pra reordenar** filhos já existentes, use `parent.insertChild(parent.children.indexOf(nodeDeReferencia), noArrumar)` — recalcule o índice a cada insert, porque ele muda depois de cada chamada; (b) **pra colocar algo "ao lado" de um conteúdo já existente** (não empilhado verticalmente), NÃO crie como filho direto do auto-layout — ache/crie um frame NÃO-auto-layout aninhado (frames simples com filhos por posição absoluta continuam aceitando `x`/`y` normalmente) e dê `appendChild` nele, widening o frame pra caber o novo conteúdo (`frame.resize(novaLargura, frame.height)`). Ex. real: chip "Tipo" (`Bug visual`) só ficou ao lado de "Risco alto" depois de vir pra DENTRO do frame de severidade (não-auto-layout, 84×20) em vez de tentar ser irmão solto no painel (auto-layout vertical, itemSpacing 16) — e o bloco "Detalhes técnicos" só ficou ANTES do bloco técnico original depois de 2 `insertChild` (não de ajustar `y`). (2026-07-26, painel lateral de Riscos do Hub de Design)
