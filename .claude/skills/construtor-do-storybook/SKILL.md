# Storybook Builder — nosso Storybook do DS (fiel ao código)

> **Agente 9** (ver [`memoria/agentes.md`](../../../memoria/agentes.md)). Constrói/mantém o Storybook standalone que documenta o DS **as-is do código**. Réplica fiel de componente no Figma → `codigo-ao-figma` (A1); design novo → `estudio-de-design` (A2); regras → `regras-de-negocio` (A3); tokens/mapa → `mapa-do-design-system` (A4).

## Filosofia
**O Storybook mostra o componente REAL, renderizado a partir do código vivo — não uma reimplementação.** Toda story importa o `.vue`/`.ts` do <PRODUTO> via alias do Vite; todo token vem do código. Se você se pegou "recriando" um componente ou digitando um hex à mão, parou de documentar e começou a inventar — volte à fonte. Igual A1/A7: **código = fonte da verdade**, `<PRODUTO>/` é **read-only** (você escreve só no projeto `../design-system/`).

## Contexto herdado (não reinvente)
- O `webclient` **já tem Storybook 10.4.6 rodando** dentro do repo: `<PRODUTO>/webclient/.storybook/` (`main.js`, `preview.js`, `preview-head.html`, `main.css`) + 6 stories em `src/stories/`. O `preview.js` já resolve o mais difícil: `setup()` com `app.provide` de `t`/`event`/`alert`/`helper` + router de memória, import de `bootstrap`/`sweetalert2`/`datepicker`/`<empresa>.scss`, e um decorator de `v-model` reativo. **Porte isso** — é o ponto de partida testado.
- Stack a espelhar (do `package.json`): Storybook `10.4.6`, `@storybook/vue3-vite`, Vue `3.5`, Vite `7`, `sass`, addons `@storybook/addon-a11y`, `@storybook/addon-docs`, `@chromatic-com/storybook`, `@storybook/addon-onboarding`.
- Padrão de story bom já existe: `<PRODUTO>/webclient/src/stories/EdsButton.stories.js` — `title: 'Components/…'`, `tags: ['autodocs']`, `argTypes` agrupados por `table.category` (Appearance/Content/State/Testing), uma export por estado. **Siga esse padrão.**

**Alias é o coração do consumo:** no `viteFinal`/vite config, `resolve.alias['@<produto>'] = <<PRODUTO>/webclient/src>` (e replique os aliases que o `vite.config.js` do webclient usa — ex.: `@` interno). Import na story: `import EdsButton from '@<produto>/components/buttons/EdsButton.vue'`. Assim o componente é sempre o do código.

## Golden Path

### Fase 0 — Scaffold e PROVE o consumo (o passo que de-risca tudo)
1. `~/bin/<produto>-sync` (repo fresco, read-only).
2. Crie `../design-system/` como projeto irmão: git init, `memoria/` (copie o esqueleto dos outros projetos), symlinks `.claude`/`<PRODUTO>`/`.claude/references` (ver `../../../docs/README-workflow.md`).
3. `npm init` Vue3 + Vite + Storybook 10 **nas mesmas versões do repo**.
4. Config: alias `@<produto>`; import de SCSS/`<empresa>.scss` + **fonts Satoshi estáticas** (por peso — Bold/Medium/Regular; **nunca** "Satoshi Variable", falta no ambiente); porte `preview.js` (provides + decorator).
5. Copie `EdsButton.stories.js` (e +1) apontando o import pro alias → `npm run storybook`. **Critério de pronto da Fase 0:** o EdsButton renderiza no Storybook **a partir do código-fonte vivo** (mexer no `.vue` do repo reflete). Se não renderiza (provide faltando, SCSS, font, dep transitiva), **conserte o consumo aqui** — não avance com base quebrada.

Documente que **dois sistemas coexistem** (EDS novo × legado `ath`).
- **Typography:** Doc Block `Typeset` com a escala EDS real (Display 32/Title 24/Subtitle 20/Text L 16/Text M 14/Caption 12 × Bold/Medium/Regular), usando as CSS vars `--eds-*`.
- **Shadows** (L1–L6), **Spacing**, **Radius**, **Icons** (galeria Phosphor do set usado).
- **Regra:** gere programaticamente a partir da fonte sempre que der (ler o JSON/SCSS e mapear) — Foundation digitada à mão drifta e mente.
- **[comprovado Fase 1] SEMÂNTICOS: renderize do CSS var VIVO + compute o hex em runtime** (`getComputedStyle(document.documentElement).getPropertyValue(cssVar)`), com o `<empresa>.scss` no preview — é a verdade do código rodando. O DTCG serve p/ nome/ordem/ref e p/ **primitivas** (que não são CSS var). **Sinalize drift** (badge quando hex vivo ≠ ref do DTCG): achado real — DTCG dizia `content-warning=yellow.500`, código usa `yellow-600`. Importe o DTCG via alias `@tokens` → realpath de `.claude/references/ds-contract` + `fs.allow`.
- **[Fase 1] Espaçamento no <PRODUTO> não é coleção de CSS var** — é convenção de classe `ath-*` (nº no nome = px, base rem 10px). Documente como é, com os valores REAIS mais usados (grep), sem inventar tokens.
- **Foundations = componentes Vue + stories CSF** (não doc-blocks React) num Storybook de Vue: controle total + fidelidade viva. Para a QUALIDADE editorial do conteúdo (anatomia, when-to-use, do&don't, a11y), a skill irmã **`documentacao-do-ds` (A10)** escreve o MDX no padrão de DS de classe mundial — A9 renderiza, A10 documenta.

### Fase 2 — Componentes (incremental por categoria)
Ordem sugerida (valor × prontidão): **buttons** (Eds já tem) → inputs/selects → tables → modais → badge/tag/pill → cards → checkbox/accordion → breadcrumb/navbar/tabs → resto.
Por componente:
1. **Leia a superfície no código** (props, emits, slots, estados) — props enum/boolean, `computed` de estilo, `v-if`/`v-else-if`, estados CSS. Use a técnica do A1 (ou consulte A1/A3) quando não estiver óbvio.
2. **Docs page:** o quê / quando usar / do & don't (peça a copy ao `estudio-de-design` se for elaborar).
3. **Playground:** todas as props como `argTypes` com controls, agrupadas por `table.category` (padrão do EdsButton).
4. **Uma story por estado/variante** (primary/secondary/…, sizes, loading, disabled, com ícone, com badge…). Cubra **Ath\* e Eds\***.
5. `tags: ['autodocs']` + `title` na hierarquia `Components/<Categoria>/<Nome>`.

### Fase 3 — Patterns & polish
- **Patterns** (MDX) compondo componentes reais: página filtro+tabela, formulário (vee-validate), fluxo de modal (`AthModal`).
- **Theming do manager** (`.storybook/manager.ts` + tema) com cores EDS + logo → o Storybook "parece nosso".
- **a11y** ligado (addon já no setup); rode contraste WCAG (reuse `codigo-ao-figma/references/wcag-contrast.py`) e **reporte** — não conserte o componente (fidelidade). Use a **régua** [`ds-migration-checklist-ath-to-eds.md`](../../references/ds-migration-checklist-ath-to-eds.md) como checklist do que reportar (a11y/token/CSS/estrutura); os gaps recorrentes do legado já estão catalogados com caso real.

### Fase 4 — Hosting (só quando pedirem)
- `build-storybook` → `storybook-static/`. Deploy Vercel (estático) / Chromatic (review visual, já instalado) / Lovable.
- **Source no build:** o alias aponta pro repo local; no CI/deploy o código-fonte precisa existir → submodule, snapshot versionado, ou `<produto>-sync` no build step. **Vendorizar sem sinalizar = drift silencioso** (proibido).

## Pitfalls (vão crescer com o uso)
- **[comprovado] `addon-vitest` = o "build≠renderiza" AUTOMATIZADO (rede de segurança permanente).** Roda CADA story como teste num browser headless (Playwright/Chromium) e falha se a story quebrar/renderizar vazio — exatamente a verificação que eu fazia na mão. **Vale muito a pena.** Receita: instalar **pinado** (`@storybook/addon-vitest@<mesma-versão-do-SB>` + `vitest@^4` + `@vitest/browser@^4` + `@vitest/browser-playwright@^4` — o browser-playwright é `^4` only); `vitest.config.ts` com `storybookTest({ configDir: '.storybook' })` (herda TODA a nossa config SB: alias `@<produto>`, compilador Vue único, mock de provider, render global) + `setupFiles: ['.storybook/vitest.setup.ts']` que reusa o `preview.ts`. **Gotcha 1 (vitest 4):** `browser.provider` virou **factory** — `import { playwright } from '@vitest/browser-playwright'` + `provider: playwright()` (não a string `'playwright'`). **Gotcha 2:** rodar ~500 stories com N browsers em paralelo **derruba o chromium no startup** (`playwright JSON parse "Unexpected end of JSON input"`) → **`test.fileParallelism: false`** (serial; ~20s p/ 496 stories, estável). Desde SB 10.3 o addon aplica o preview automaticamente (o setup com `setProjectAnnotations` é opcional). Resultado real: 126 files / **496 tests passed**. Rode no CI + antes de fechar tarefa.
- **[Fases 1/3/4, comprovado] Theming, patterns e hosting — receitas.** (1) **Manager theming:** `import { create } from 'storybook/theming/create'` + `import { addons } from 'storybook/manager-api'` num `.storybook/manager.ts`; cores = tokens Brand/Neutral do código; `brandImage: '/img/logo-primary.png'` (servido via `staticDirs`). (2) **Patterns = SFCs que compõem componentes REAIS** (`@<produto>`) em `src/patterns/` + stories `title:'Patterns/…'` com `render` explícito; `<Form>` de vee-validate + inputs funcionam (provides/diretivas já no preview). (3) **Hosting:** `build-storybook` gera estático **auto-contido** (componentes inlined, fonte+phosphor embutidos) → deployável em QUALQUER host; o clone `<PRODUTO>/` só é preciso no BUILD (o alias resolve em build-time). CI (Vercel git) precisa do fonte → submodule/snapshot; por ora **buildar local + publicar o estático** (ou Chromatic, que sobe o build). `vercel.json` com SPA rewrites pronto.
- **[Fase 2, comprovado — MDX] `{palavra}` em prosa MDX = expressão JS → quebra em RUNTIME** ("`palavra` is not defined"), mesmo com **build verde** (compila, mas o `{ }` vira expressão e a var não existe). Ex. real: `"Remover {opção}"` derrubou a Docs page inteira. **Sempre** envolva chaves literais em **crase** (`` `{opção}` ``) ou escape (`\{`). Vale pra `{id}`, `{name}`, `{size}`… — se NÃO estiver dentro de crase, quebra. Detecção: sweep headless das **Docs pages** procurando "is not defined"/"failed to render" no innerText (o build não pega isto — é o "build≠renderiza" da camada MDX).
- **[Fase 2c, comprovado] Componentes que buscam de API (ex.: `Ath*Select*`) → MOCKE o provider central, não reimplemente.** O `provider` do <PRODUTO> é um singleton com gateways (`core`/`identity`/…) populados na init do app — no Storybook ficam `undefined` → `provider.core.get()` quebra → select vazio. **Fix:** um mock (`.storybook/mock/provider-mock.ts`) que faz `provider.addProvider(gw, axiosLike)` p/ cada gateway, retornando `{ data: lista }`. A `lista` é um **array espelhado nas chaves de acesso comuns** (`arr.items = arr; arr.data = arr; arr.result = arr; …`) — cobre `response.data` (maioria) E `response.data.items`/`.result`/… numa resposta só. Cada item traz **os campos de rótulo REAIS** que os selects usam (grep `label-prop`/`value-prop`: `name`/`label`/`displayName`/`legalName`/`studentName`/`code`/`id`/…). **Enriqueça pelo CONSUMIDOR:** o sweep headless revela campos aninhados faltando (TypeError `reading '0'`/`forEach` em `opt.companies[0]`) → adicione `companies:[…]`/`areas:[…]` ao item. Instale `installProviderMock()` no TOPO do `preview.ts` (antes de montar; services leem provider em call-time). Também proveja stubs de `permission`/`feature`/`setting`/`environment`/`preloader`.
- **[Fase 2c] Componente gated em permissão (host/tenant global) → decorator de story ISOLADO.** Se as opções só montam sob `permission.isHost() && isTenantSelectedIsGlobal()`, mantenha o mock GLOBAL conservador (false, p/ não mudar o estado de outros) e proveja um `permission` host+global **só naquela story** via `decorators:[() => ({ setup(){ provide('permission', {…}) }, template:'<story/>' })]`.
- **[Fase 2c] Workflow: `args` chega como STRING, não array → script vê `[]` e roda 0 agentes SILENCIOSAMENTE.** Passar `args:[…]` no tool virou string no script (`Array.isArray(args)` false). **Sempre cheque `agent_count`** no resultado do workflow — 0 agentes + result vazio = problema de input, não "nada a fazer". **Fix:** deixe o script **self-contained** (hardcode a lista) ou `JSON.parse` se `typeof args==='string'`.
- **[Fase 2c] Fan-out que funciona (comprovado 2×):** Workflow/subagentes escrevem stories em paralelo + REPORTAM gaps (schema estruturado) → orquestrador faz **1 build + 1 sweep headless** (sinal forte) → conserta só os que falham. 35 selects: 6 agentes escreveram, o sweep pegou 3 (1 branco por prop de contexto faltando, 2 TypeError por campo aninhado no mock) → fix central → 36/36.
- **[CRÍTICO — comprovado] `build-storybook` VERDE ≠ componente RENDERIZA. Verifique num browser HEADLESS.** O build compila/resolve, mas um componente pode montar VAZIO (render silencioso) e o build passa. **Já enganou 2×** aqui (Fase 0/1 "verdes" mas as stories montavam sem rótulo). **Verificação obrigatória:** `npm i -D playwright` + `npx playwright install chromium`, então carregue `iframe.html?id=<storyId>&viewMode=story`, pegue `#storybook-root` innerText/innerHTML e os `console`/`pageerror`. **Sweep de saúde:** 1 story por família (agrupe por `title` no `index.json`), sinalize as com innerHTML < ~15 chars (tirando `<!--comments-->`) como branco. iframe HTTP 200 NÃO prova render (é client-side).
- **[CRÍTICO — comprovado] Remover o docgen do SB quebra DUAS coisas silenciosamente** (o docgen foi removido pra ter 1 compilador de SFC — ver pitfall do double-compile). (1) **Slots param de mapear:** o `getSlots` do SB só vira arg→slot quando `argTypes[key].table.category === 'slots'` (setado pelo docgen). Sem docgen, o arg `default` (rótulo do botão etc.) não vira slot → componente monta VAZIO. **Fix:** `render` global no `preview.ts` que mapeia `default → slot` padrão (e mantém v-model). (2) **`render()` com `template:` string precisa do COMPILADOR em runtime** — o build Vite do Vue é runtime-only → template não compila, monta `<!---->` (warning "runtime compilation is not supported"). **Fix (o que destrava tudo):** `resolve.alias.vue = 'vue/dist/vue.esm-bundler.js'`. Isso conserta o render global + TODAS as stories/Foundations que usam `template:` em `render`. Sem essa alias, metade do Storybook fica em branco mesmo com build verde.
- **[comprovado] Asset de CSS/fonte vindo de S3 (ex.: `phosphor.css`) → CORS bloqueia em localhost** (o app carrega da origem dele, ok; o Storybook em `localhost:6006` não). Ícones somem. **Fix:** vendorize local — `curl` o CSS (server-side ignora CORS), salve em `public/`, sirva via `staticDirs`, e aponte o `preview-head.html` pro caminho local. O phosphor.css do <PRODUTO> já traz a fonte embutida em base64 (self-contained, ~3.5MB) → só o CSS basta.
- **[Fase 2 wave, comprovado] MDX companheira (`<Meta of={CSF}>`) + `tags:['autodocs']` no MESMO CSF = ERRO de indexação** ("You created a component docs page… but also tagged the CSF file with 'autodocs'"). Quando o A10 escreve uma `X.mdx` com `<Meta of={XStories}/>`, **remova `tags:['autodocs']`** do `X.stories.ts` (a MDX passa a SER a página Docs). Fronteira A9×A10: ao adicionar MDX, o A9 tira o autodocs daquele CSF.
- **[Fase 2 wave] Abrir overlay/estado é no nível da STORY, não do preview.** Modal por **prop/v-model** (`show`/`modelValue`) → abre por arg. Modal/painel por **evento global** (o `event` do preview é no-op) → proveja um **event bus REAL e ISOLADO por story** (`new TinyEmitter()`, a mesma lib de `helpers/event`) e emita pós-mount (o filho já registrou o listener). Modal **full-screen** (`position:fixed`, `100vw/vh`, `Teleport to body`) → **não** dá pra conter com `transform`; use um **gatilho real (EdsButton)** que abre. Sempre com **disclosure** de que é setup mockado.
- **[Fase 2 wave] NÃO use `decorators` de meta pra bounding/slot.** O decorator global do preview faz `<story v-bind="args">`; um `decorators` intermediário não repassa args → quebra props/v-model. Use **`render` com `v-bind="args"`** no componente real; v-model reativo dentro do render via `ref` local sincronizado.
- **[Fase 2 wave] Pinia precisa estar instalado no preview** (`app.use(createPinia())`) — componente com `useXStore()` **no setup** quebra o mount sem ele (não dá pra consertar por decorator de story — é nível-app). Se além disso chama serviço HTTP no `onMounted`, precisa **mock de serviço** (ver camada de mock de provider). **`inject` não-provido só quebra se ACESSADO no setup** — se o uso está atrás de `v-if`/handler, dá pra storyar com dados-mock que evitam o ramo (reporte que aquele estado não fica documentado).
- **[Fase 2 wave] Múltiplos v-model** (ex.: `min-value`/`max-value`) não são cobertos pelo decorator (só `modelValue`) → ligue **cada** v-model no `render` da story e use `inheritAttrs:false` no componente do render pra o fallthrough do decorator global não duplicar. **Componentes que MUTAM o array de props** (`tab.isActive = …`) exigem **array inline por story** (senão vaza estado entre stories na página de autodocs).
- **[Fase 2 wave] `v-eb-tippy` (tooltip) é gap recorrente** — o app usa tippy.js (fora das deps). Registre uma diretiva LEVE central (`el.title = binding.value` quando string): some o warning, render limpo, tooltip rico não abre (documente). Não instale tippy só pra isso.
- **[Fase 2 wave] Fan-out que só ESCREVE + valida CENTRAL.** Subagentes A9 em paralelo no MESMO projeto: cada um escreve stories da sua categoria, **não roda build, não edita `.storybook/*`, e REPORTA os gaps de provide/serviço/diretiva**. O orquestrador aplica os fixes central no preview e roda **UM** build de validação. Evita corrida de escrita e preview inconsistente. (Achados de drift do código — hex cru, classe que não bate com o CSS, arquivo .vue vazio, emit com nome divergente — vão pra `melhorias.md` como achado, nunca "corrigidos" no repo read-only.)
- **[Fase 2, comprovado — CRÍTICO] Storybook de Vue tem UM compilador de SFC próprio que NÃO alcança .vue externos e CONFLITA com `@vitejs/plugin-vue`.** O `@storybook/vue3-vite` injeta dois plugins: `storybook:vue-template-compilation` (compila SFC) e `storybook:vue-docgen-plugin` (prop-table automática) — ambos **escopados ao root**, então **não transformam os `.vue` externos** vindos pelo alias (erro: *"Expression expected (you need plugins to import files that are not JavaScript)"*). Se você adiciona um `@vitejs/plugin-vue` seu pra cobrir os externos, os DOIS compiladores processam o mesmo arquivo → **double-compile** → *"Element is missing end tag"* numa **linha ALÉM do EOF** (ex.: 1457 num arquivo de 1454), **mesmo o arquivo sendo válido**. **Diagnóstico decisivo:** parseie o `.vue` isolado com `@vue/compiler-sfc` (`parse()` + `compileTemplate()`); **0 erros = o problema é interação de plugin, não o arquivo.** **Fix (em `.storybook/main.ts` → `viteFinal`):** remova AMBOS os plugins Vue do SB e adicione **UM** `@vitejs/plugin-vue` seu (processa root + externos):
  ```ts
  const SB_VUE = new Set(['storybook:vue-template-compilation','storybook:vue-docgen-plugin'])
  const strip = (ps) => (ps||[]).map(p=>Array.isArray(p)?strip(p):p).filter(p=>!p || (p.name!=='vite:vue' && !SB_VUE.has(p.name)))
  cfg.plugins = strip(cfg.plugins); return mergeConfig(cfg, { plugins:[vue()], ... })
  ```
  **Trade-off:** perde o **docgen automático** (prop-table inferida do componente) → **declare `argTypes` explícitos** nas stories (a gente já faz). Um único compilador some com o erro; build fica verde.
- **[Fase 2] Componentes legados/complexos precisam de provides E diretivas globais que o app registra fora do `main.ts` do SB.** O `preview.ts` do repo só mocka `t`/`event`/`alert`/`helper`+router. Faltavam: **`provide('format')`** e **`provide('date')`** (de `@/helpers/*`), e as diretivas **`money`** (`v-money`), **`maska`** (`maska/vue`) e **`click-outside`** (copie a def inline de `@/app/config/directives`, NÃO importe o `installDirectives` — ele puxa `eb-tippy`/tippy.js fora das deps). Sem `format`, inputs de máscara dão **TypeError no mount**; sem as diretivas, renderizam sem máscara/sem fechar. Também: `<teleport to="#portal-footer-body">` (rodapé de seleção do `EdsTable`) precisa do alvo → crie um `<div id="portal-footer-body">` no **`.storybook/preview-body.html`**. Regra: componente que injeta/usa diretiva não-mockada → **mocke central no preview**, não reimplemente; registre o que mockou.
- **[Fase 0, comprovado] Import bare de arquivo FORA do root não resolve → `resolve.dedupe` de TODO o runtime.** Como os componentes vivem fora do root do projeto (código read-only via alias), um `import 'currency.js'`/`'date-fns'` dentro deles **não acha o `node_modules` do storybook** (o clone `webclient/node_modules` nem existe) e o build quebra (`Rollup failed to resolve import "currency.js"`). Só `vue` resolvia — porque estava em `dedupe`. **Fix:** liste **todas** as deps de runtime do webclient em `resolve.dedupe` (dedupe força resolução a partir do root deste projeto) **e** copie o bloco `dependencies` do `package.json` do webclient pro nosso. Feito em `.storybook/main.ts`.
- **[Fase 0] <PRODUTO> é symlink → use o realpath no alias E no `fs.allow`.** O Vite segue symlinks; se você liberar só o caminho lógico, ele bloqueia o arquivo real. `fs.realpathSync` no alias `@`/`@<produto>` e em `server.fs.allow` (incluir a pasta de fontes). Sem isso, "The request url is outside of Vite serving allow list".
- **[Fase 0] Assets `/img/*` (logo/ícones) vêm do `public/` do webclient → `staticDirs`.** O `<empresa>.scss`/componentes referenciam `/img/logo-primary.png` etc. (absolutos). Mapeie `staticDirs: [{ from: <webclient>/public, to: '/' }]`. Fontes (`@font-face url()` relativo) o Vite processa e emite como asset hasheado — não precisam de staticDir, só de `fs.allow` (confirmado: 9 arquivos Satoshi bundlados).
- **Dep transitiva pesada.** Um componente pode importar store/serviço/provider/i18n. O `preview.js` do repo já mocka os provides comuns (`t`/`event`/`alert`/`helper`/router); se faltar outro, **mocke no setup do preview** (não reimplemente o componente). Registre o que mockou (cobertura honesta).
- **SCSS/tokens não carregados** → componente renderiza "pelado". Garanta o import do `<empresa>.scss` (e a cadeia de temas) no `preview`, igual o repo faz.
- **Satoshi "Variable"** ausente → texto cai em fallback. Use as 3 estáticas por peso (self-hosted), como o código.
- **Alias divergente do webclient.** Se o `.vue` usa `@/...` internamente, replique TODOS os aliases do `vite.config.js` do webclient no config do storybook, senão o import quebra fundo na árvore.
- **Escrever no repo por engano.** Nunca. Só `../design-system/`. Symlink `<PRODUTO>` é read-only.
- **Digitar hex/valor na Foundation.** Sempre da fonte (JSON/SCSS). Se digitou, vira dívida de drift.
- **Fingir cobertura.** Storyou 20 de 163? Diga 20. Mockou um serviço pra renderizar? Diga. As-is honesto.
- **[Docs] Mock fixo de `feature`/`permission` esconde ramos inteiros do template.** O preview mocka `feature.hasFeature → false` e `permission.hasPermission → true`. Componentes com bloco gated por feature (ex.: `AthPanelFilesUpload` → switch de assinatura só aparece com `hasFeatureContractDigitalSignature`) renderizam SÓ o ramo que o mock libera — mesmo com a prop ligada. Enumere o que o preview trava e diga na doc (a11y/estado desse ramo se valida no filho ou no app real), não finja que funciona.
- **[Docs] Docstring do componente pode MENTIR — verifique o render real.** `AthInputTextFake` tem `@summary` "input desabilitado", mas renderiza um `<div class="form-control">` (não `<input disabled>`), então o `:has(:disabled)` do tema nunca casa → aparece no estado **default**, não disabled. A verdade é o que a SFC efetivamente monta, não o JSDoc dela.
- **[Docs] Antes de concluir "não renderiza por falta de dep", cheque imports TRANSITIVOS reais (grep).** Comentário do preview dizia "tippy.js fora das deps"; `AthPanelFilesTableDownloadDelete` importa `moreActionsTable → eb-tippy/ebTippyDirective`, mas `grep "from 'tippy'"` mostrou **zero** import — o util constrói o próprio tooltip via DOM/crypto (self-contained) e o build passou. O aviso era sobre a DIRETIVA registrada, não sobre este util.
- **[Docs] `title:` define o agrupamento na sidebar — siga os vizinhos, não a pasta do código.** `AthPanelFilesUpload` (código em `inputs/uploads/`) → `Components/Panels/`; `AthPanelFilesTableDownloadDelete` (código em `tables/`, mas construído sobre `EdsTable`) → `Components/Tables/`.
